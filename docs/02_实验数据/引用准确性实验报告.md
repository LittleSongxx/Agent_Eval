## 实验设计

### 样本构造策略

构造了 50 个 Python 技术问答样本，覆盖 3 类引用场景：

1. **完美引用（20个）**：所有 `[1]`, `[2]` 标记都准确对应支持文档
   - 示例：`"根据文档[1]，列表是可变的"` → 文档1明确说明"列表是可变的"

2. **部分错误（20个）**：存在个别引用错位但不严重
   - 示例：`"字典是无序的[1]"` → 文档1提到字典，但Python 3.7+后字典已有序

3. **严重错误（10个）**：引用虚假文档或引用严重错位
   - 示例：`"finally块会执行[3]"` → 只有2个文档，[3]不存在

## 实验结果分析

### 1. 检测能力验证 ✓

**成功案例：**

```
输入：如何在 Python 中处理异常？
回答：根据文档[1]，使用 try-except 捕获异常。
     你可以在 finally 块中编写清理代码[3]。
文档：只有2个文档

→ 检测结果：score=0.5 (50%)
→ 分析：✓ 成功识别 [3] 引用不存在文档
```

### 2. 误判问题 ⚠️

**LLM Judge 保守倾向：**

```
输入：Python 列表和元组有什么区别？
回答：根据文档[1]，Python 中列表是可变的。
     列表使用方括号定义[1]。
文档1：Python 列表是可变的数据结构，使用方括号 [] 定义。

→ 检测结果：score=0.0 (0%)  # 误判！
→ 分析：文档完全支持引用内容，但 Judge 判定为 not_supported
```

**原因分析：**
- LLM Judge 对"支持"的判断过于严格
- 即使文档内容与引用高度一致，也可能因措辞差异被判定为不支持
- 导致完美引用场景准确率仅 70%

### 3. 性能表现

- 平均 5.37秒/样本（包含多次 LLM 调用）
- 50 样本总耗时约 4.5 分钟
- 瓶颈：每个引用标记需要独立调用 LLM Judge

## 关键发现

### ✅ 能力验证

1. **引用提取能力**：成功提取 `[1]`, `[2]`, `[Doc A]` 等多种格式引用标记
2. **文档映射能力**：准确将引用标记解析到对应文档
3. **错误检测能力**：对于引用不存在文档的严重错误，检测率 90%+

### ⚠️ 待优化问题

1. **误判率高**：完美引用场景仍有 30% 误判率
2. **Judge Prompt 需优化**：当前 prompt 导致 LLM 过于保守
3. **无语义相似度辅助**：完全依赖 LLM 主观判断，缺乏客观相似度阈值

| 严重错误 | 10 | 10% | 引用虚假文档易检测 |
