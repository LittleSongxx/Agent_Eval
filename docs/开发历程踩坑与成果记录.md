## 二、分阶段详细记录

### 阶段 0：MVP 搭建（04-21 ~ 05-12）

**做了什么**：前后端初始化 → 评测引擎（LLM-as-a-Judge，双层 prompt：系统层管输出协议、
业务层判分标准存 DB 可覆盖）→ 数据集管理 → RAG 数据集生成器（结构化文档切分 +
LLM 问题生成）→ 接口实时评测与自定义指标链路 → 多轮/Agent 场景支持。

**踩的坑**：
- **加密密文问题**（`52d84ed`）：LLM 配置的密钥在存储/回显链路有加解密不一致，
  导致配置无法正确回读。解决：统一加密/解密路径，补测试。
- 早期同主题提交多次出现（`73c1008`/`86f00ad`、`942f3ea`/`58bc4a2` 等成对出现），
  是历史整理时的重提交，与功能无关。

**成果**：平台全链路可用（前端评测页 + 报告详情页 + 数据集管理 + 后端引擎），
`5042e3e` 合并进 main。

### 阶段 0.5：开源准备（06-17 ~ 07-20）

README 中英文拆分、发布前清理、roadmap + v0.1.0 changelog。无实质踩坑。

### 阶段 1：评测可靠性 + 元评价体系（08-06，`b90c2ba`）

**做了什么**：加权总分（场景快照权重聚合）、Judge 可靠性量化（`EVAL_JUDGE_SAMPLES`
多采样 + 采样标准差 + 低置信度标记）、成本统计、人工一致性（kappa）、WebSocket
实时进度、任务陈旧回收、RAGAS 对照脚本 + 元评价方法论文档。

**踩的坑**（每个都是"问题表现 → 根因 → 最小修复"）：
1. **WebSocket 跨事件循环线程安全**：后台任务线程推送进度到主事件循环，直接推会
   竞态。解决：线程安全推送封装 + 断线自动回退轮询。
2. **任务陈旧回收误杀**：长任务被误判为陈旧而回收。解决：心跳机制防误杀。
3. **RAGAS 0.4.3 导入即崩**：langchain-community 0.3+ 移除了 `vertexai` 模块，
   RAGAS 仍硬编码导入。解决：项目内最小 shim（`backend/scripts/_shims/`），
   仅对照实验运行时生效，不污染平台代码。
4. **Qwen3 thinking 模式把调用拒了**：RAGAS 的 answer_relevancy 一次请求 n=3，
   默认开启 thinking 的模型拒绝。解决：ChatOpenAI 注入 `extra_body={"enable_thinking": false}`。
5. **embedding 长度安全路径损坏输入**：langchain 默认走 tiktoken 白名单路径，
   模型名不在白名单导致 input 损坏。解决：`check_embedding_ctx_length=False` 走直传路径。

**成果**：评测结果从"一个数"变成"可信可复现的数字"；元评价四层体系（区分度/
结构效度/信度/实用性）落地为文档 + 实验脚本。

### 阶段 2：双通道指标 + Judge 工程化 + 评测集治理（08-06，`9eee48d`）

**做了什么**：
- **双通道指标**（全部原生实现，不依赖第三方评测框架）：
  - 生成式相关性：反推问题 + OpenAI 兼容 embedding 语义相似度；
  - 断言级忠实度：原子断言拆解逐条核验；
  - 与整体判定指标并存交叉验证。
- **Judge 工程化**：强制 CoT（`JUDGE_COT_MODE`）、换序互评防位置偏置
  （`EVAL_SWAP_CHECK`：反转列表字段复评 + 一致性聚合）、多裁判面板
  （`judge_llm_config_ids`：均值/多数票聚合 + 裁判间 MAD）。
- **人工校准闭环**：报告自动算人工 vs 自动 Cohen's kappa，<0.7 提示修订判分标准。
- **数据集版本化**：行级变更自增版本，任务创建时冻结 dataset_version。
- **评测集治理工具**：零依赖中文 BM25 mock 检索引擎、检索噪声实验、n-gram +
  embedding 双信号污染检测。

**成果**：76 测试通过；生成侧从单一判定升级为"整体 + 断言级/生成式"双通道。

**⚠ 事后发现的坑（重要）**：本阶段提交信息宣称噪声实验"验证通过：MRR 1.0→0.09
随噪声单调下降"——**该实验后来（阶段 6）被证明是闭式循环**：检索结果是
`noise_ids + reference_ids` 拼出来的，MRR 恒等于 1/(n+1)，与数据无关。教训：
"数字单调下降"本身不能证明测量有效，必须先证明测量结果依赖真实数据。

**做了什么**：前端评测执行页新增附加裁判 LLM 多选（排除主裁判，克隆任务继承面板）。

**验证**：76 测试通过 + 前端构建通过 + 全模块导入 OK。

### 阶段 4：claim 分解质量（08-06，`d60c15c`）

**踩的坑（验收发现的真实质量问题）**：分解 prompt 把评价性句子当"无信息量"
过滤 → **答非所问的行分解为空断言 → 触发 1.0 宽松兜底 → 忠实性虚高**。
空断言兜底改 0（未基于上下文作答 = 未扎根，与 RAGAS 行为一致），同时保留
意见性断言（可被上下文支持或反驳）。

**验证**：错误注入集复验——无关回答行 claim 0.0（"今天天气不错 ✗ / 适合散步 ✗"
逐条可读），四指标全部归零，双通道口径一致。新增空断言兜底=0 测试，79 通过。

### 阶段 5：RAGAS 对照实测 + 缺陷 A/B（工作区，本次提交）

对照实验最大产出不是"自研指标和 RAGAS 有多像"，而是照出**平台自己的两个测量污染缺陷**。

**缺陷 A：样本真值标签泄露给裁判**。评测集每行带 `generation_meta =
{"kind": "correct|hallucinated|truncated"}`，下发 payload 的兜底循环把样本内
所有字段无差别交给裁判 → **100 个 judge prompt 里 64 个带标签** → 区分度和
一致性同时虚高（裁判锚定标签后换序互评自然更"稳定"）。
**解决**：`_JUDGE_HIDDEN_FIELDS` 黑名单 + 单元 + 端到端两层回归测试；关闭修复后
泄露立即重现，证明测试不是空转。

**缺陷 B：`required_fields` 不约束实际下发字段（口径越界）**。`required_fields`
只校验"字段是否存在"，不裁剪 payload，于是检索侧指标看得见 `response`、只判
"是否回应问题"的 answer_relevancy 看得见 `reference`。
**证明因果**（A/B 实验 `ab_response_leak.py`，同批 8 条幻觉样本唯一变量是
`response` 有无）：context_recall 0.7875→1.0000、context_precision 0.8125→1.0000，
与 RAGAS 逐行一致。
**修复过程的第二个发现：原定方案本身是错的**。"按 `required_fields` 严格裁剪"
会打断 17 个内置指标里的 **9 个**：8 个 Agent/多轮指标判的就是 AI 回复却没把
`response` 列为必需（运行时才注入，列为必需会让 dataset 模式整批判缺失）；
`context_precision` 的判定文字要看 `reference` 而它不声明必需。
**根因**：一个字段被当成两件事用——校验门槛 vs 裁判可见范围，两个集合本就不相等。
**实际修复**：拆出独立 `judge_fields` 口径，17 个指标逐个显式声明；`_sample_payload`
新增白名单模式并整段跳过兜底循环（缺陷 A 与 B 的共同载体）。5 个回归测试 +
结构不变量测试（每个 spec 的 judge_fields 覆盖 required_fields）。

**过程中的技术坑**：A/B 脚本 `sys.path` 指向 `/tmp` 导致 0 字节输出（路径 bug）；
报告 JSON 的 `rows` 是计数不是列表（TypeError）。均为定位修复。

**修复后 n=25 实测**（RAGAS 逐行分复用、逐行核对未变）：
- 检索侧：context_recall / context_precision **逐行等于 RAGAS**，分层总偏离
  0.275→0.000、0.213→0.000——平台检索侧那点方差 100% 是缺陷 B 的产物，无一是检索信号；
- 生成侧如实说明：answer_relevancy 幻觉样本偏离 0.284→0.028，但与 RAGAS 相关性
  略降（0.439→0.373）——**泄露此前掩盖了一个真实机制差异**：拿掉 `reference` 后
  裁判对截断样本两极判断，而 RAGAS 的反推问题 + embedding 相似度结构上惩罚不了截断。
  决策：选择声明口径的正确性，而不是相关性数字；
- 双通道优势在修复后扩大：Pearson +0.047→+0.071、Spearman +0.007→+0.061，
  截断样本上断言级偏离是整体版的 1/3.6。

**测试非空性验证**：用 pytest 插件 monkeypatch 模拟修复前行为（不改源码），
3 个 bug-guard 测试如预期失败、过修正守卫测试仍通过——证明测试真实抓 bug。

### 阶段 6：检索侧补齐（工作区，本次提交）

**坑（最值钱的一个）**：阶段 2 提交的"已验证"噪声实验是**闭式循环**。动手前先做
数值验证：`noise_ids + reference_ids` 的构造下金标恒定排第 n+1 位，MRR ≡ 1/(n+1)、
HitRate@5 ≡ (n<5)——与数据集内容、检索器质量、chunk 文本全部无关，换一份完全
不相干的数据也是同一串数字。**把它当区分度证据是循环论证**，原脚本废弃。

**解决**：重写为真实 BM25 检索——
- 检索结果唯一来源是 BM25 排序，任何位置不拼 `reference_context_ids`；
- 双干扰语料：无关 26 段（`_fixtures/distractor_corpus.md`，手机/咖啡/编程/旅行，
  零词汇重叠）+ 同域难负例 10 段（`_fixtures/hard_negatives.md`，虚构"优选商城"
  售后政策，同主题同术语不同数字）；
- **守门测试 `test_ranking_is_data_dependent`**：把金标正文换成无关文本后 H@1 必须
  归零——同义反复的实现过不了这条，防回归。

**实测**（25 条互异查询，每条 1 个金标 ID）：

| 场景 | 库 | H@1 | H@3 | H@5 | MRR |
|------|----|-----|-----|-----|-----|
| 纯知识库（无干扰） | 6 | 1.000 | 1.000 | 1.000 | 1.000 |
| 无关干扰 ×全部(26) | 32 | 0.960 | 1.000 | 1.000 | 0.980 |
| 同域难负例 ×全部(10) | 16 | 0.880 | 1.000 | 1.000 | 0.940 |
| 无关全部 + 难负例全部 | 42 | **0.840** | 1.000 | 1.000 | **0.913** |

**解读**：无关干扰几乎不掉（主题可分，词面匹配足够）；**同域难负例才是真压力**——
"7天无理由退货的起算时间"输给"优选商城支持5天无理由退货…自签收次日起算"，只差
一个数字，bigram 层面不可分。这是真实检索质量信号，也是"为什么需要向量检索/精排"
的教科书证据。金标掉排名的行同时出现在 correct 与 hallucinated 两类中（与
"检索质量和生成质量解耦"的分层设计一致）。

**坑：规则版 precision 不可校准**。原方案把"查询覆盖度阈值法"当证据之二，实测
按句覆盖度（阈值 0.4）纯知识库下仅 0.13、整 chunk 覆盖度 0.21，且随难负例注入
**反向微升**（硬负例与金标共享词汇，覆盖度无法区分）——短中文问句词项太少，
该启发式无判别力。与其报一个不可解释的数字，**移除并在脚本注释里记录原因**；
规则版对标改走 RAGAS NonLLM（业界校准过，不重复造轮子）。

**结构效度补齐：RAGAS NonLLM 规则版对标（同日）**。用 `compare_ragas_nonllm.py`
（dump 平台环境 / score RAGAS 环境两阶段隔离）把同一批 BM25 检索输出喂给 RAGAS
v0.4.3 NonLLMContextRecall / NonLLMContextPrecisionWithReference（Levenshtein
归一化相似度阈值 0.5，零 LLM 零 embedding，完全确定性）：

| 场景 | 平台 H@1 | 平台 MRR | RAGAS NonLLM recall | RAGAS NonLLM precision |
|------|------|------|------|------|
| 纯知识库 | 1.000 | 1.000 | 1.000 | 1.000 |
| 无关干扰 ×全部 | 0.960 | 0.980 | 1.000 | 0.980 |
| 同域难负例 ×全部 | 0.880 | 0.940 | 1.000 | 0.940 |
| 无关全部 + 难负例全部 | 0.840 | **0.913** | 1.000 | **0.913** |

**逐场景 MRR ≡ NonLLM precision**——机制是单金标下 RAGAS ContextPrecision 的
AP ≡ 1/rank ≡ 平台 MRR 的数学等价，但两个**独立实现**（ID 级精确命中 vs 字符级
相似度判定）在同一批检索上交叉验证，检索侧结构效度证据成立（确定性 ↔ 确定性，
跳过 LLM 判定差异干扰）。NonLLM recall 恒 1.0 与平台 H@5 恒 1.0 同因（金标总在
top-5 内，饱和边界共享同一检索输入）。行级 Spearman -1.0 是 AP=1/rank 的数学
必然，全 tie 场景无定义（报告记 None）。

**准则效度补齐：检索侧人工黄金集（同日）**。25 条查询逐条标注「期望命中的
chunk」（最重压力场景）：初标 + 用户人工逐条严格复核 **25/25 一致**，人工审核
确认为最终真值（`retrieval_goldset_annotations.json`，provenance 含人工复核
记录；标注表 docs/检索侧黄金集标注表.md；评分
`compute_goldset_agreement.py` → `retrieval_goldset_agreement.json`）。
结果：判定分布 **Y 23 / MULTI 2 / N 0**——人工审核未发现金标构造错误；
金标 ∈ 人工期望集 25/25（"每条查询唯一 source chunk"的合成构造成立）；
金标口径与人工黄金集口径 H@1/MRR 完全一致（0.840/0.9133）。2 条多来源
（行 6/19：验收后退款时限跨第 2 节退货流程与第 8 节售后时效重复）金标均 top-1

### 阶段 9：标注模型重构——把"上界"从不可测变成可测（工作区，本次提交）

**动机（一条推理链，不是需求列表）**：judge-人 kappa 的天花板是**人-人 kappa**。
两个人自己都只能达到 0.65 一致的任务上，judge 拿到 0.8175 不代表它准，只代表它
**拟合了这一个标注者的偏好**——这种情况下**数字越高越可疑，不是越可信**。而旧
数据模型里，一行结果只有一套 `manual_status / manual_score / manual_tags /
manual_note / reviewed_at` 列，**物理上只能存一个标注者**，所以人-人 kappa 不是
"还没算"，是**算不出来**。阶段 7/8 给 0.8175 加了三条统计限定（CI、in-sample、
基线敏感性），但那三条都在问"这个数字抖不抖"，这一步问的是另一个问题：
**这个数字的参照系是什么**。

**做法：投影（materialized view）模式，而不是全量迁移。**
新增 `row_annotations` 表作为真值（`row_result_id + annotator + is_adjudication`
唯一约束），`manual_*` 五列降级为**派生投影**，由 `core/annotation.py::
project_annotations_onto_row` **单点重算**。选投影而非直接改所有调用点的原因：
前端 **46 处**引用（`types/index.ts` + `ReportDetailPage.tsx`）、后端 3 个离线脚本
（`dual_channel_arbitration` / `calibration_compare` / `kappa_significance`）都读这
五列，一次改完等于把"重构"和"迁移"两类风险绑死在一起。**尤其是那三个脚本用的是
裸 SQL**（`SELECT ... manual_status FROM eval_row_results`，绕开 ORM），换句话说
任何"靠模型层兼容"的方案对它们都无效，投影是唯一能让它们零改动继续跑的做法——
而它们产出的正是阶段 7/8 那批已发表数字。代价是派生数据可能漂移，用两件事控住：
唯一写入点 + 真库不动点测试。

投影按四级优先级裁决（`effective_annotation`，纯函数）：
1. **仲裁**（`is_adjudication=True`，取最新一条）——仲裁者已经看过双方标签；
2. **单标注者**——必须与旧字段**逐字段相等**（向后兼容的硬约束）；
3. **一致**（多人同判）——分数取均值、标签取并集、备注加标注者前缀；
4. **未解决分歧**——投影成 `needs_review`。

第 4 条是刻意的：`needs_review` 不在 `BINARY_STATUSES` 里，因此**自动被 kappa
排除**。理由是**人自己都没定论的标签不能当真值用**——猜一个（比如取第一个
标注者）等于把分歧偷偷变成事实。同理，仲裁记录**不参与人-人统计**：仲裁者已经
看过两边标签，算进去会**抬高上界**，而上界一旦被抬高，"judge 超过上界"这个信号
就再也测不出来——那是循环论证，不是测量。

**上界取 min 不取 mean**（`pairwise_annotator_kappa`）：judge 只要超过**任意一对**
人的一致度，"它拟合了某一个人"的怀疑就已经成立；取均值会把这个信号平均掉。
人-人 kappa 只在**共同标注的行**上算（`overlap_n` 一并报出）——把"某人没标的行"
当成分歧会**凭空造出冲突**。

**judge-vs-上界用配对 bootstrap，没有新增检验机制**（`judge_ceiling_comparison`）：
`[(A_i, B_i)]` 和 `[(A_i, judge_i)]` 逐行共用参照列 A，正好落进阶段 8 已有的
`paired_kappa_delta_ci` 的行对齐守卫里。四种状态：`ceiling_unknown` /
`insufficient_overlap` / `judge_above_ceiling`（**这是警告，不是通过**）/
`within_ceiling`。k 个标注者产生 k*(k-1) 个有序对，**多重比较只披露不校正**
（报 `comparison_count` + `multiplicity_note`）——n=25 下做 Bonferroni 会把所有
信号擦掉，把问题藏起来比暴露出来更糟。

**四个坑：**

1. **只在 n≥2 标注者时才炸的时区坑。** SQLite 的 DATETIME 不存时区，写进去的
   aware datetime 读回来是 naive，两者相比 →
   `TypeError: can't compare offset-naive and offset-aware datetimes`。但**一条
   标注排序不做任何比较**，所以重构后第一次写入、第一轮自测全都正常，直到第二位
   标注者进来才炸——而"第二位标注者"恰好就是这次重构的**唯一目的**。修在
   **比较入口**（`_as_naive_utc`）而不只是写入端：写入端不止一处（回填 SQL、API、
   测试构造），漏一处就复发。
2. **文档引用了一个不存在的测试。** `annotation.py:27` 和 `database.py:117` 两处
   注释都写着"投影是不动点，由 `test_projection_has_no_drift_on_real_labels`
   保证"——那个测试**当时并不存在**，我只用一次性脚本验过就写下了这句话。这正是
   本项目存在的意义所指的那类缺陷：**声称有证据，证据其实没入库**。已补齐，并
   额外补 `TestBackfillCodePath`（原测试只检查历史结果，抓不到回填代码的回归）。
3. **`py_compile` 抓不到未定义名字。** 我先写了 report.py 的 import，后加常量，
   中间态 `NameError: ANNOTATION_PAYLOAD_FIELDS is not defined` 以 500 的形式到了
   运行时（还被 `raise_server_exceptions=False` 掩了一层）。补 **pyflakes 关卡**
   ——它当场就能抓到，顺带揪出重构遗留的两个死 import。
4. **备份文件名绕过了 `.gitignore`，差点把 API Key 提交上去。** 动迁移前我备份了
   真库为 `eval_platform.db.bak-p1-1-<时间戳>`——`.gitignore` 里有 `*.db`，但
   **`*.db` 匹配不到 `.db.bak-...`**（后缀不再是 `.db`）。于是这个文件处于可提交

   制造一个新的泄露面**，安全规则要按"文件内容"而不是"当时想到的那个扩展名"写。

**还有一次自己制造的假 ✅（值得单独记）**：我一度打印了"所有已发表数字逐位复现"

`ModuleNotFoundError: No module named 'app'`（`python scripts/x.py` 把 `scripts/`

**迁移安全**：`_backfill_row_annotations` 是全项目唯一写数据的迁移，三条性质写进

## 三、贯穿性方法论（可迁移，面试可讲）

1. **先质疑测量本身**。本项目的三次大坑（闭式循环、标签泄露、口径越界）本质是
   同一个问题：数字好看，但测量对象与声称的对象不一致。每次都是"先证明测量有效，
   再读数字"。
2. **修复前先枚举全部调用点**。judge_fields 方案若直接按原定方案做会打断 9/17
   指标；动手前枚举 17 个内置指标避免了这次破坏。"一个字段两个职责"是根因，
   拆分职责而非加特例。
3. **测试必须证明非空转**。关闭修复 → 测试失败（缺陷 A/B 都验证过）；守门测试
   用"数据变了结果必须变"来防同义反复。
4. **报告数字必须带来源**。合并报告每个指标带 `_provenance`（数据来源文件、
   运行时间、缺陷修复状态），任何数值不靠人工转抄。
5. **诚实的取舍**。规则版 precision 移除、answer_relevancy 相关性下降的机制解释、
   检索侧绝对数值不具工业意义的边界声明——报可解释的数字，不报好看的数字。
6. **最小 shim 原则**：第三方库兼容问题用项目内 shim 解决（`_shims/`），
   平台代码零依赖第三方评测框架（避免被误认为 fork RAGAS/DeepEval）。
7. **一个数字必须有参照系，否则它不是结论**。阶段 7/8 问的是"0.8175 抖不抖"，
   阶段 9 问的是"0.8175 的上界是多少"——后者发现旧数据模型**物理上算不出**人-人
   kappa。**指标越高越可疑**的场景是真实存在的（judge 只是拟合了唯一标注者的偏好）；
   测不出上界时，正确做法是**把"测不出"显式印出来**，而不是让读者自行把裸数字
   当成"够准了"。
8. **变异测试是测试有牙的唯一证据**。写完测试要反过来往源码里种 bug：改坏一处 →
   必须有测试变红，且**红的原因要对得上**。阶段 9 种了 5 个变异全部被杀（含
   "上界取均值而非最小值"这种只错一个函数名的改动）。测试通过只说明代码此刻没坏，
   变异被杀才说明测试真的在守。

## 五、遗留与已知边界

1. **检索侧**：NDCG（排序质量分层）、语料规模太小导致 H@3/H@5 饱和（NonLLM
   recall 恒 1.0 同因）。区分度（BM25 实测）、结构效度（RAGAS NonLLM 对标）、
   准则效度（人工黄金集）三证齐全（阶段 6）。
2. **校准重跑的任务中断教训**（2026-08-06）：任务 11 首次重跑因服务重启被
   startup recovery 标记 failed（进度 0.16，仅 5 行）——评测任务运行期间**严禁
   重启后端**（recovery 会无条件标记 running 任务失败）；且新进程需显式带
   EVAL_JUDGE_SAMPLES=5（新 bash 会话不保留 export，environ 验证后才算数）。
   已重建任务 12 重跑。
3. **answer_relevancy 与 RAGAS 的机制差异**（截断惩罚）是真实差异而非缺陷，
   文档已如实记录；双通道仲裁可作后续方向。
4. **faithfulness 不惩罚截断是定义边界**（与 RAGAS 一致，业界共识）：只测"已说出的
   claim 是否 grounded"，完整性由 answer_relevancy 负责——**不要试图"修"它**。
5. **kappa 的样本量边界（已用自家 bootstrap 算出具体数字，不再是经验值）**：
   n=25 下基线 kappa 0.4582 的 95% CI 是 **[0.1325, 0.7634]**、校准后 0.8175 的是
   **[0.5192, 1.0]**，两个区间各自横跨 Landis-Koch 多个档位；配对 bootstrap 的
   Δkappa = 0.3593、95% 双侧 CI **[-0.013, 0.672]**（下界压着 0，单侧 95% 才为正，
   P(Δ>0)=0.9665）。另有两个独立的量级折扣：① 0.8175 是**在样本内**测的（阈值和
   判分标准都是看着任务 10 那 7 条分歧改出来的，再回到同 25 行复测），偏乐观；
   ② 同配置重跑的噪声底 0.0643（任务 9 vs 10）占声称效果的 17.9%。
   **正确表述是"方向明确、量级待定"**；按同一 bootstrap 外推，**n=50 就能让双侧
   下界离开 0**（CI [0.117, 0.588]），这也是 P1-3 扩样到 60-100 条的直接动机。
   部署决策必须等扩样后的样本外复测。
6. **人-人 kappa 上界当前测不出来（n=1 标注者）**：阶段 9 把上界从"物理上无法计算"
   变成"可计算但当前无数据"——25 条标注全部出自 `reviewer_1`，所以报告如实输出
   `ceiling_unknown`。**这不是"judge 通过了"，是"没有参照物"**：判 0.8175 够不够好，
   取决于两个人类标注同一批数据能达到多少。若人-人只有 0.65，那 0.8175 measure 的
   是"judge 拟合了这一位标注者的偏好"，**数字越高越可疑**。补第二位标注者是
   P1-3 扩样时的同批动作（同一批 60-100 行，双标）。另注：标注者身份目前是
   **自声明**（请求体里的 `annotator` 字段，API 鉴权属 P2），所以"两个独立标注者"
   靠流程保证而非系统保证——一个人可以伪造出虚高的人-人 kappa。
7. 中间报告 `_n10` / `_n25_clean` 未入库（合并报告只引用 `_n25` 与 `_n25_scoped`），
   `ragas_comparison_checkpoint.json` 为断点续跑临时产物，已 gitignore。
