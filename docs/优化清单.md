### P0-1: Agent 轨迹级评测 ⬜

**为什么是 P0**：
- 面试高频话题（A14/A22 必问"Agent 调试和 badcase 分析"）
- 2026 业界前沿（TRAJECT-Bench、VAKRA 都在做轨迹评测）
- 展示"不只看结果，还看过程"的评测设计能力

**实现内容**：
- [ ] 新增 `TrajectoryFaithfulnessMetric`（轨迹忠实度）
  - Agent 推理步骤与工具返回结果是否一致
  - 数据格式：`agent_trajectory = [{"step": 1, "thought": "...", "tool": "...", "result": ...}]`
- [ ] 新增 `ErrorRecoveryMetric`（错误恢复能力）
  - 工具调用失败后是否有合理的降级或重试
- [ ] 新增 `ToolSelectionRationalityMetric`（工具选择合理性）
  - 当前步骤是否选择了最优工具（LLM Judge 判定）
- [ ] 构造 30 个 Agent 样本数据集
  - 包含：正常执行、推理错误、工具失败、次优工具选择
- [ ] 运行实验并输出报告
  - 轨迹忠实度均值、错误恢复率、工具选择合理性
  - 与结果层 Task Completion 的相关性分析

**验收标准**：
- ✅ 3 个新指标单元测试通过
- ✅ 30 个样本评测完成，生成 JSON 报告
- ✅ 实验报告 Markdown 文档（含数据表格和结论）
- ✅ 能用 1 分钟流畅讲出核心数字

**预期数据**：
```
轨迹级评测实验（n=30 Agent 样本）：
- 轨迹忠实度均值 0.87（13% 样本存在推理与工具返回不一致）
- 错误恢复率 0.60（40% 样本遇错直接终止，无降级）
- 工具选择合理性 0.92（8% 样本可用更优工具）
- 轨迹级指标与结果层 Task Completion 相关性 Spearman 0.73
```

**文件清单**：
- `backend/app/core/evaluation_engine.py`（新增 3 个 Metric 类）

### P0-2: RAGAS v0.4 归因对照实验 ✅

**完成时间**：2026-08-17  
**实际工作量**：1 天（遇到 RAGAS 依赖问题，改为独立实现）

**为什么是 P0**：
- 前沿对标能力（引用准确性是金融/法律/医疗场景刚需）
- 企业级刚需（检测"引用文档 A 但内容来自文档 B"的错位问题）
- 技术深度展示（独立实现 LLM-as-a-Judge 评测逻辑）

**实际完成内容**：
- ✅ 新增 `CitationAccuracyMetric`（引用准确性）
  - 提取引用标记：支持 `[1]`, `[Doc A]`, `根据文档X` 等格式
  - 构建文档索引映射：数字索引、字母索引
  - LLM Judge 判断：被引用文档是否真正支持内容
  - 计算引用准确率 = 正确引用数 / 总引用数
- ✅ 构造 50 个测试样本
  - 完美引用 20 个、部分错误 20 个、严重错误 10 个
  - 覆盖 Python 技术问答场景
- ✅ 运行实验并生成报告
  - 整体预测准确率 52%（容差 15%）
  - 严重错误检测率 90%+
  - 平均耗时 5.37秒/样本
- ❌ RAGAS v0.4 对照实验未完成
  - 原因：`langchain_community.chat_models.vertexai` 依赖冲突
  - 决策：限时 10 分钟修复无果，切换 Plan B 独立实现

**验收结果**：
- ✅ CitationAccuracy 指标实现并集成到 evaluation_engine
- ✅ 50 样本测试完成，生成 JSON 报告
- ✅ 实验报告 Markdown 文档：`docs/02_实验数据/引用准确性实验报告.md`
- ✅ 面试材料提炼（1分钟版本）

**关键数据**：
```
引用准确性评测实验（n=50 样本）：
- 整体预测准确率：52% (26/50，容差 15%)
- 完美引用检测准确率：70% (14/20)
- 严重错误检测率：90%+ (9/10)
- 平均耗时：5.37秒/样本
- LLM Judge 保守倾向：30% 误判率（将正确引用判为不支持）
```

**核心发现**：
1. **能力验证**：成功检测引用虚假文档、引用错位等问题
2. **误判问题**：LLM Judge 过于保守，导致完美引用误判率 30%
3. **优化方向**：引入语义相似度辅助，减少 LLM 主观判断依赖

**文件清单**：
- `backend/app/core/evaluation_engine.py`（CitationAccuracyMetric 实现，449-647 行）
- `backend/datasets/citation_samples.json`（50 个测试样本）
- `backend/scripts/citation_accuracy_experiment.py`（实验脚本）
- `backend/scripts/citation_quick_test.py`（快速测试脚本）
- `backend/citation_accuracy_report.json`（实验报告 JSON）
- `docs/02_实验数据/引用准确性实验报告.md`（详细实验报告）

**面试话术（1分钟）**：
> "我实现了引用准确性评测指标，检测 RAG 回答中'引用文档 A 但内容来自文档 B'的错位问题。用正则提取引用标记，构建文档索引映射，然后用 LLM Judge 判断被引用文档是否真正支持内容。在 50 个测试样本上，整体准确率 52%，对严重错误检测率达 90%。发现 LLM Judge 存在保守倾向，提出了引入语义相似度辅助的优化方案。原计划与 RAGAS v0.4 对照，但遇到依赖冲突，限时 10分钟修复无果后果断切换到独立实现路线，确保了功能按时交付。"

### P0-3: 成本优化实验 ⬜

**为什么是 P0**：
- 企业级关注点（成本是 AI 应用落地第一门槛）
- 可量化对比（能拿出"成本降 40%、耗时降 60%"的数字）
- 展示工程能力（不只会调包，还会算账和优化）

**实现内容**：
- [ ] 新增配置项
  - `EVAL_METRIC_CONCURRENCY`（指标级并发数，默认 1）
  - `EVAL_BATCH_SIZE`（批量推理批次大小，默认 1）
  - `EVAL_COST_MODE`（fast/balanced/accurate）
- [ ] 实现指标级并发
  - 行内多个指标并发执行（需注意 token 计数归属）
- [ ] 实现批量推理
  - 多行样本打包成一个 Judge 请求
  - 适配 OpenAI batch API
- [ ] 运行 4 组对照实验
  - 基线（串行）
  - 行并发=4
  - 行并发=4 + 指标并发=3
  - 批量推理 batch=5
- [ ] 输出成本-耗时-质量权衡曲线

**验收标准**：
- ✅ 新配置项生效，通过单元测试
- ✅ 4 组实验数据完整，生成对比表格
- ✅ 质量未劣化（mean_std 变化 <10%）
- ✅ 能讲出"最优解是批量推理，成本降 40%、耗时降 75%、质量几乎不变"

**预期数据**：
```
成本优化实验（n=25×6=150 次 Judge 调用）：
- 基线（串行）：180s / 0.52 元
- 行并发=4：52s / 0.52 元（耗时降 71%，成本不变）
- 指标并发=3：22s / 0.53 元（耗时降 88%，成本增 2%）
- 批量推理 batch=5：45s / 0.31 元（耗时降 75%，成本降 40%）
- 结论：批量推理是成本-耗时最优解
```

**文件清单**：
- `backend/app/core/config.py`（新增配置项）
- `backend/app/core/evaluation_engine.py`（指标并发 + 批量推理实现）
- `backend/scripts/cost_optimization_experiment.py`（实验脚本）
- `docs/02_实验数据/成本优化实验报告.md`（实验报告）
