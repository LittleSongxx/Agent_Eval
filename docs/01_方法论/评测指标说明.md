# AI 评测指标与场景实践指南

> 本文档系统梳理 AI 评测平台支持的所有评测场景、评测指标的计算原理、数据采集方法和实际使用建议。
> 适用于评测工程师、AI 开发者、产品经理阅读，可用于向团队和管理层介绍评测体系。

---

## 一、评测的基本原理

### 1.0 与 Ragas / DeepEval 的关系

本项目不是 Ragas 或 DeepEval 的二次封装，当前代码也不依赖它们：

| 对象 | 工程依赖 | 本项目的关系 |
|------|----------|--------------|
| Ragas | 无依赖，不安装、不 import、不调用其服务 | 指标概念层面对齐 RAG 评测常见术语，例如 Faithfulness、Context Recall、Context Precision、Answer Relevancy |
| DeepEval | 无依赖，不安装、不 import、不调用其服务 | 指标分类层面参考其 Agentic Metrics、RAG Metrics、Multi-Turn Metrics 的组织方式 |
| OpenAI-compatible LLM | 有依赖 | 平台通过 OpenAI SDK 调用你配置的评判模型，由本项目自己的 Judge Prompt 输出分数和理由 |

因此，本平台的定位是：**参考业界通用评测指标，但由平台原生实现指标执行、评分提示词、确定性计算和报告展示**。这样可以减少第三方库版本锁定，也便于加入中文业务指标、Agent 工具链指标和多轮对话指标。

需要注意的是，虽然部分指标名称与 Ragas / DeepEval 相同，但分数不承诺与它们库里的实现逐项完全一致。报告里的分数和理由以本平台当前文档定义和实现逻辑为准。

### 1.1 三个角色

整个评测过程涉及三个角色：

```
┌─────────────┐          ┌──────────────┐          ┌──────────────┐
│  被测 AI 系统 │  ──输出→  │  评测数据集    │  ──送入→  │  评测 LLM     │
│  (你开发的)   │          │  (你收集+标注) │          │  (裁判，如千问) │
└─────────────┘          └──────────────┘          └──────────────┘
```

| 角色 | 是谁 | 做什么 |
|------|------|--------|
| **被测 AI 系统** | 你开发的 RAG/Agent/对话机器人 | 产出回答、检索结果、工具调用等——这些是被评测的对象 |
| **评测数据集** | 你收集和标注的测试数据 | 包含测试输入 + 被测系统输出 + 人工标注的标准答案 |
| **评测 LLM（裁判）** | 通义千问/GPT-4 等 | 阅读数据，像考官一样给被测系统的输出打分 |

### 1.2 离线评测的工作流

```
第一步：在平台外运行你的 AI 系统
  用户问题 → 你的系统 → 回答 + 检索结果 + 工具调用日志

第二步：收集输出，填入数据集
  把系统的回答、检索结果等复制到评测平台的数据集中
  对关键用例，人工写标准答案（reference）

第三步：选择评测指标，执行评测
  评测 LLM 逐条阅读数据，按指标逻辑打分

第四步：查看报告，改进系统
  根据低分项和评分理由，定位问题并优化
```

### 1.3 自动评测 + 人工评测的双闭环

平台现在不只有自动评测，还支持两种人工参与方式：

1. **人工盲测**
   - 适合比较两个模型、两个 chat 接口，或新旧版本的主观回答质量
   - 核心问题是“同一条样本下，A 和 B 谁更好”

2. **结果级人工复核**
   - 适合对普通评测报告里的单条结果做人工判断
   - 核心问题是“自动结论是否可信，这条样本后续怎么处理”

推荐闭环：

```text
离线自动评测
  -> 找到关键失败样本 / 高风险样本
  -> 用人工盲测比较两个候选方案
  -> 对争议样本补结果级人工复核
  -> 结合分数、胜率、人工备注做上线判断
```

这样平台既能规模化跑分，也能保留业务判断。

## 二、三大评测场景

### 2.0 人工盲测场景

人工盲测不是第四个“指标场景”，而是一种跨场景的评测方法。它可以作用在 RAG、Agent、多轮对话等任意数据集上，只要样本里有 `user_input`，就能拿同一批输入分别请求两个应答端，交给人做主观比较。

**适用问题**：

- 两个模型谁回答更自然、更完整？
- 新版 chat 接口是否真的比老版好？
- 自动指标差不多时，哪个方案业务上更可接受？

**当前支持的对比对象**：

- `LLM 配置 vs LLM 配置`
- `Chat 接口 vs Chat 接口`
- `LLM 配置 vs Chat 接口`

**执行方式**：

- 后台自动生成 A / B 两边回答
- 默认样本级并发 `3`
- 每条样本的 A / B 两边会同时请求

**投票方式**：

- 左侧更好
- 右侧更好
- 都好
- 都不好

**重要说明**：

盲测时的“左侧 / 右侧”只是展示位置，每条样本会随机交换顺序；报告中的 `A 胜 / B 胜` 是去盲后的真实结果。平台已经在汇总区和逐条明细里显示左右与 A/B 的对应关系，避免误读。

### 2.1 RAG（检索增强生成）评测

**适用对象**：基于检索的问答系统——用户提问，系统先检索知识库，再基于检索到的内容生成回答。

**评什么**：
- 检索到的内容对不对？（上下文召回率、上下文精确度）
- 回答有没有瞎编？（忠实度）
- 回答跟问题相关吗？（回答相关性）
- 回答跟标准答案一致且完整吗？（事实正确性、答案完整性）

**数据集字段**：

| 字段 | 类型 | 从哪来 | 是否必须 |
|------|------|--------|---------|
| `user_input` | text | 你设计的测试问题 | 必须 |
| `response` | text | 从你的 RAG 系统收集的回答 | 必须 |
| `retrieved_contexts` | text_list | 从你的 RAG 检索模块收集的文档片段 | 部分指标需要 |
| `reference` | text | 你人工写的标准答案 | 部分指标需要 |
| `retrieved_context_ids` | text_list | 从检索模块收集的文档/分片 ID，顺序与 retrieved_contexts 一致 | 检索单测需要 |
| `reference_context_ids` | text_list | 人工标注的标准文档/分片 ID | 检索单测需要 |

**RAG 指标分层**：

| 层级 | P0 核心指标 | 解决的问题 |
|------|-------------|------------|
| 检索质量 | Context Recall、Context Precision、Contextual Relevancy（扩展） | 是否漏召回、是否召回太多噪声、上下文整体是否贴题 |
| 生成可信度 | Faithfulness、Factual Correctness | 是否基于证据、事实是否正确 |
| 回答质量 | Answer Relevancy、Answer Completeness | 是否答到问题、是否覆盖关键要点 |
| 检索单测 | HitRate@K (Hit Rate at K)、MRR (Mean Reciprocal Rank) | 有文档 ID 时，判断是否命中正确文档及排序是否靠前 |

> 默认 RAG 问答模板启用前 6 个 P0 指标。`Contextual Relevancy` 是检索质量扩展指标，适合你想单独判断“检索内容整体是否贴题”的场景。`HitRate@K`（Hit Rate at K）和 `MRR`（Mean Reciprocal Rank）是信息检索领域通用指标，需要额外采集 `retrieved_context_ids` 与 `reference_context_ids`，适合做“只评检索器”的单测或高级检索报告。

**数据采集实例**：

假设你有一个内部知识库问答系统：

```
1. 用户在系统里提问：「公司年假政策是什么？」

2. 你的系统在知识库里检索到 2 段文档：
   retrieved_contexts = [
     "根据公司制度，正式员工入职满1年享有5天年假，满3年10天，满5年15天。",
     "年假需提前3个工作日申请，经直属领导审批后生效。"
   ]

3. 你的系统基于检索结果生成回答：
   response = "公司年假政策：入职满1年5天，满3年10天，满5年15天。需提前3天申请。"

4. 你人工写一个标准答案（可选）：
   reference = "正式员工入职满1年有5天年假，满3年10天，满5年15天。需提前3个工作日申请并经领导审批。"

5. 填入数据集，执行评测
```

### 2.2 Agent（智能体）评测

**适用对象**：能调用工具的 AI 助手——用户下达任务，Agent 决定调用哪些工具，最终完成任务。

**评什么**：
- Agent 是否完成任务闭环？（Task Completion）
- Agent 调的工具对不对？（Tool Correctness）
- 工具参数是否正确？（Argument Correctness）
- 是否多调、漏调或重复调用工具？（Step Efficiency）
- 最终结果是否准确达成用户目标？（Goal Accuracy）

**它和“多轮对话评测”的区别**：

Agent 评测关注的是“行动是否正确”。样本可以是单轮任务，也可以是多轮任务，但核心证据是 Agent 的执行轨迹：它是否调用了正确工具、参数是否正确、工具返回后是否完成目标。即使对话轮次不多，只要涉及工具、外部系统或明确任务闭环，也应该优先归到 Agent 场景。

**数据集字段**：

| 字段 | 类型 | 从哪来 | 是否必须 |
|------|------|--------|---------|
| `user_input` | conversation | 从 Agent 运行日志采集的完整对话 | 必须 |
| `reference` | text | 你写的「期望达成的目标」 | Task Completion / Goal Accuracy 需要 |
| `reference_tool_calls` | tool_call_list | 你写的「期望调用的工具」 | Tool Correctness / Argument Correctness / Step Efficiency 需要 |
| `reference_role` | text | Agent 应遵守的角色和职责边界 | 角色一致性类扩展指标需要 |
| `retrieved_contexts` | text_list | 任务相关的工具/业务背景资料 | 多轮可信度类扩展指标需要 |

**Agent 指标分层**：

| 层级 | 指标 | 判断重点 |
|------|------|----------|
| Agent 任务 | Task Completion、Goal Accuracy | 是否完成任务闭环，最终结果是否符合用户目标 |
| Agent 工具 | Tool Correctness、Argument Correctness | 工具是否选对，参数是否正确 |
| Agent 过程 | Step Efficiency | 执行步骤是否高效，是否存在多余、重复或缺失步骤 |

**对话数据格式说明**：

```json
[
  {"type": "human", "content": "帮我查订单 ORD-001 的物流"},

  {"type": "ai", "content": "好的，我来查一下。",
   "tool_calls": [{"name": "query_logistics", "args": {"order_id": "ORD-001"}}]},

  {"type": "tool", "content": "{\"carrier\": \"顺丰\", \"status\": \"派送中\"}"},

  {"type": "ai", "content": "您的订单由顺丰承运，目前正在派送中。"}
]
```

- `human`：用户说的话
- `ai`：Agent 的回复。如果它决定调工具，`tool_calls` 里记录调了什么工具、什么参数
- `tool`：工具返回的结果

**数据采集实例**：

```
1. 你的 Agent 系统在生产环境处理了一个用户请求
2. 从日志中提取完整的对话记录（human → ai → tool → ai ...）
3. 你人工标注：
   - reference = "成功查询到物流状态并告知用户"
   - reference_tool_calls = [{"name": "query_logistics", "args": {"order_id": "ORD-001"}}]
4. 填入数据集
```

### 2.3 多轮对话评测

**适用对象**：客服机器人、对话助手等需要多轮交互的系统。

**评什么**：
- 对话有没有跑题？（Topic Adherence）
- 每轮回答是否回应当前用户问题？（Turn Relevancy）
- 整段对话是否完成用户需求？（Conversation Completeness）
- AI 有没有忘记之前的对话内容？（Knowledge Retention）
- AI 是否遵守指定角色和职责边界？（Role Adherence）
- 多轮回复是否基于资料，不跨轮幻觉？（Turn Faithfulness，扩展）

**它和“Agent 评测”的区别**：

多轮对话评测关注的是“对话体验是否稳定”。它不要求工具调用，也不重点检查外部动作是否完成，而是检查多轮上下文是否衔接、是否围绕业务话题、是否前后矛盾。只要没有工具执行链，或者你暂时只关心对话质量而不是任务执行，就用多轮对话场景。

| 维度 | Agent 评测 | 多轮对话评测 |
|------|------------|--------------|
| 核心问题 | 是否正确使用工具并完成任务 | 是否围绕话题、上下文连贯 |
| 样本类型 | 单轮或多轮都可以，多轮最常见 | 多轮 conversation |
| 关键字段 | `reference_tool_calls`, `reference` | `reference_topics`, `reference`, `reference_role` |
| 典型指标 | Task Completion, Tool Correctness, Argument Correctness, Step Efficiency, Goal Accuracy | Topic Adherence, Turn Relevancy, Conversation Completeness, Knowledge Retention, Role Adherence |
| 典型失败 | 调错工具、参数错误、任务没完成 | 跑题、忘上下文、前后矛盾 |

**数据集字段**：

| 字段 | 类型 | 从哪来 | 是否必须 |
|------|------|--------|---------|
| `user_input` | conversation | 从对话日志采集 | 必须 |
| `reference` | text | 你写的期望对话结果 | 对话完成度需要 |
| `reference_topics` | text_list | 你根据业务规则定义的允许话题 | 话题遵守度需要 |
| `reference_role` | text | AI 应遵守的角色、职责边界和语气要求 | 角色遵守度需要 |
| `retrieved_contexts` | text_list | 多轮回复可依据的业务资料 | 轮次忠实度需要 |

**多轮对话指标分层**：

| 层级 | 指标 | 判断重点 |
|------|------|----------|
| 对话相关性 | Topic Adherence、Turn Relevancy | 是否围绕业务话题，每轮是否贴合当前用户输入 |
| 对话完成度 | Conversation Completeness | 整段对话是否满足用户需求并完成期望结果 |
| 上下文记忆 | Knowledge Retention | 是否记住用户已提供的事实、偏好、订单号、时间等 |
| 角色一致性 | Role Adherence | 是否遵守指定角色、职责边界和语气要求 |
| 多轮可信度 | Turn Faithfulness | 多轮回复是否基于检索上下文或给定资料 |

**reference_topics 从哪来**：

这不是从对话里采集的，而是你根据业务规则定义的：

```
客服机器人允许讨论的话题 = ["订单查询", "退货退款", "物流追踪", "账户问题", "产品咨询"]

如果机器人在对话中跑去推荐股票，话题遵守度就会扣分。
```

## 三、全部指标详解

### 3.1 指标总览

| 指标 | 中文名 | 适用场景 | 需要人工标注 | 分数范围 | 核心问题 |
|------|--------|---------|------------|---------|---------|
| Faithfulness | 忠实度 | RAG | **不需要** | 0~1 | 回答有没有瞎编？ |
| Context Recall | 上下文召回率 | RAG | 需要 reference | 0~1 | 检索到的文档够不够全？ |
| Context Precision | 上下文精确度 | RAG | 需要 reference | 0~1 | 检索到的文档有没有用？ |
| Contextual Relevancy | 上下文相关性 | RAG 扩展 | **不需要** | 0~1 | 检索上下文整体贴不贴题？ |
| Answer Relevancy | 回答相关性 | RAG | **不需要** | 0~1 | 回答跑题了吗？ |
| Factual Correctness | 事实正确性 | RAG | 需要 reference | 0~1 | 回答的事实对不对？ |
| Answer Completeness | 答案完整性 | RAG | 需要 reference | 0~1 | 回答有没有遗漏关键要点？ |
| HitRate@K (Hit Rate at K) | Top-K 命中率 | RAG 检索单测 | 需要 reference_context_ids | 0 或 1 | Top-K 是否命中标准文档？ |
| MRR (Mean Reciprocal Rank) | 平均倒数排名 | RAG 检索单测 | 需要 reference_context_ids | 0~1 | 正确文档排得是否靠前？ |
| Task Completion | 任务完成度 | Agent | 需要 reference | 0~1 | 任务闭环完成了吗？ |
| Tool Correctness | 工具正确性 | Agent | 需要 reference_tool_calls | 0~1 | 工具调对了吗？ |
| Argument Correctness | 参数正确性 | Agent | 需要 reference_tool_calls | 0~1 | 工具参数传对了吗？ |
| Step Efficiency | 步骤效率 | Agent | 需要 reference_tool_calls | 0~1 | 是否多调、漏调或重复调用？ |
| Goal Accuracy | 目标准确度 | Agent | 需要 reference | 0~1 | 最终目标达成准确吗？ |
| Topic Adherence | 话题遵守度 | 多轮对话 | 需要 reference_topics | 0~1 | AI 有没有跑题？ |
| Turn Relevancy | 轮次相关性 | 多轮对话 | **不需要** | 0~1 | 每轮回复是否回应当前用户？ |
| Conversation Completeness | 对话完成度 | 多轮对话 | 需要 reference | 0~1 | 整段对话是否解决用户需求？ |
| Knowledge Retention | 上下文记忆 | 多轮对话 | **不需要** | 0~1 | AI 是否记住前文事实？ |
| Role Adherence | 角色遵守度 | 多轮对话 | 需要 reference_role | 0~1 | AI 是否遵守角色边界？ |
| Turn Faithfulness | 轮次忠实度 | 多轮对话扩展 | **不需要** | 0~1 | 多轮回复是否基于资料？ |

## 四、结果级人工复核

### 4.1 为什么人工复核挂在“结果”上，而不是挂在“样本”上

同一条样本，在不同评测任务中的表现可能完全不同：

- 老版本接口不通过，新版本接口通过
- 模型 A 自动高分，但人工不认可
- 模型 B 自动低分，但业务上可接受

因此，人工结论默认应该挂在**某次评测任务的某条结果**上，而不是直接写死到原始样本。

平台当前的结果级人工复核字段包括：

- `manual_status`
- `manual_score`
- `manual_tags`
- `manual_note`

### 4.2 人工复核适合解决什么问题

它不是简单“加备注”，而是用来处理这几类关键情况：

1. **自动分数和业务感知不一致**
   - 自动高分，但人看着不满意
   - 自动低分，但业务方认为可接受

2. **沉淀可复用的问题类型**
   - 检索漏召回
   - 回答不完整
   - 工具参数错误
   - 角色边界不稳

3. **给后续回归和上线判断提供证据**
   - 哪些样本需要修复
   - 哪些样本需要继续复核
   - 哪些样本人工已经确认通过

### 4.3 当前页面支持的人工复核动作

在评测报告的逐条详情中，可以填写：

- 人工结论：`人工通过 / 人工驳回 / 需要修复 / 待复核`
- 人工分数
- 问题标签
- 复核备注

报告总览还会同步汇总：

- 已人工复核
- 人工通过
- 人工驳回
- 待修复 / 待复核

### 4.4 推荐使用方式

推荐不要对每条结果都人工复核，而是优先处理：

- 自动不通过的样本
- 自动分数接近阈值的样本
- 关键业务链路样本
- 盲测中出现明显分歧的样本

这样人工复核会更聚焦，也更容易沉淀价值。

---

## 五、配置前测试能力

为了减少“任务都建好了才发现打不通”的情况，平台现在支持配置阶段的前置测试。

### 5.1 LLM 配置草稿测试

在 LLM 配置弹窗里可以直接点 **测试当前配置**：

- 不需要先保存
- 使用当前表单里的草稿配置发请求
- 返回连通性结果、延迟和一小段回答预览

适合在录入新的 Base URL / API Key / 模型名时先验证是否可用。

### 5.2 Chat 接口测试

在人工盲测里，如果对比对象选择 `Chat 接口`，卡片下方会出现 **接口连通性测试**：

- 输入测试问题
- 使用当前表单里的 URL、Authorization、Headers、请求体模板发请求
- 成功后直接预览回答

这套测试尤其适合流式 SSE 接口，因为它能提前验证：

- Authorization 是否有效
- 请求体模板是否能被接口接受
- 附加 Headers 是否齐全
- SSE 返回能否被平台正确解析
| Coherence | 连贯性 | 通用 | **不需要** | 0 或 1 | 回答逻辑通顺吗？ |
| Harmfulness | 有害性 | 通用 | **不需要** | 0 或 1 | 回答有害吗？ |

### 3.2 每个指标的详细说明

---

#### 忠实度 (Faithfulness)

**一句话**：回答有没有瞎编——回答里说的每句话，是否都能从检索到的文档里找到依据。

**比较对象**：`response`（AI 回答） vs `retrieved_contexts`（AI 检索的文档）

**计算过程**：
```
① 平台原生 Judge 把回答拆成多个关键陈述
   例：「Python支持多线程，但由于GIL限制，无法真正并行」
   → 陈述1: Python支持多线程
   → 陈述2: GIL限制了真正的并行

② 对每个陈述，平台原生 Judge 检查检索文档里有没有依据
   → 陈述1: 检索文档提到"多线程" → ✓ 有依据
   → 陈述2: 检索文档只提到"互斥锁" → ✗ 没有直接依据（延伸推理）

③ 按支撑程度给出 0~1 分数，并返回具体理由
```

**实际意义**：分数低说明 AI 在「幻觉」——编造了检索文档里没有的内容。

**不需要人工标注**：只要有 user_input + response + retrieved_contexts 就能评。

---

#### 上下文召回率 (Context Recall)

**一句话**：检索到的文档够不够全——标准答案里的要点，检索文档里有没有覆盖。

**比较对象**：`retrieved_contexts`（AI 检索的文档） vs `reference`（你写的标准答案）

**计算过程**：
```
① 平台原生 Judge 把标准答案(reference)拆成多个要点
   标准答案：「GIL保证同时只有一个线程执行字节码，限制了多线程并行性能」
   → 要点1: 保证同时只有一个线程执行
   → 要点2: 限制了并行性能

② 对每个要点，平台原生 Judge 检查检索文档里有没有覆盖
   retrieved_contexts = ["GIL是CPython的互斥锁", "CPU密集型建议用多进程"]
   → 要点1: "互斥锁"间接支持 → ✓
   → 要点2: "建议用多进程"间接支持 → ✓

③ 按覆盖完整度给出 0~1 分数，并返回具体理由
```

**实际意义**：分数低说明你的检索模块**漏检了关键信息**——需要优化检索策略。

**需要人工标注 reference**。

---

#### 上下文精确度 (Context Precision)

**一句话**：检索到的文档有没有用——检索到了 5 段文档，有多少段是跟问题真正相关的。

**比较对象**：`retrieved_contexts`（AI 检索的文档）的有用性

**计算过程**：
```
① 平台原生 Judge 逐一检查每段检索文档对回答问题是否有用
   检索到3段：
   → 第1段"GIL是互斥锁" → 有用 ✓
   → 第2段"Python发布于1991年" → 无关 ✗
   → 第3段"建议用多进程" → 有用 ✓

② 考虑排序权重（有用的排前面分更高）
   第1段有用(权重高) + 第2段无关 + 第3段有用(权重低)

③ 按整体有用性给出 0~1 分数，并返回具体理由
```

**实际意义**：分数低说明你的检索模块**返回了太多无关内容**——需要提高检索精度或减少返回条数。

---

#### 上下文相关性 (Contextual Relevancy)

**一句话**：检索内容整体贴不贴题——不看标准答案，只看检索上下文是否直接有助于回答用户问题。

**比较对象**：`retrieved_contexts`（AI 检索的文档） vs `user_input`（用户问题）

**计算过程**：
```
① 平台原生 Judge 阅读用户问题和所有检索上下文
② 判断每段上下文是否直接围绕问题提供可用信息
③ 无关、只沾边、过于泛化或无法帮助回答的片段会扣分
④ 返回 0~1 分数和具体理由
```

**实际意义**：它和 Context Precision 的区别是：Context Precision 更偏“检索结果是否有用且精确”，通常会参考回答或标准答案；Contextual Relevancy 更直接看“召回内容和问题本身是否相关”。适合排查检索器召回了看似相近但实际不解决问题的内容。

---

#### 回答相关性 (Answer Relevancy)

**一句话**：回答跑题了吗——回答内容跟用户的问题是否相关。

**比较对象**：`response`（AI 回答） vs `user_input`（用户问题）

**计算过程**：
```
① 平台原生 Judge 阅读 user_input 和 response
② 判断回答是否直接回应问题，是否跑题、泛泛而谈或只回答局部
③ 按切题程度给出 0~1 分数，并返回具体理由
```

**实际意义**：分数低说明 AI 的回答**跑题了**——回答了其他内容。

**不需要人工标注**。

---

#### 事实正确性 (Factual Correctness)

**一句话**：回答的事实对不对——与标准答案在事实层面是否一致。

**比较对象**：`response`（AI 回答） vs `reference`（你写的标准答案）

**计算过程**：
```
① 平台原生 Judge 把回答和标准答案都拆成关键事实
② 逐一对比两边的事实是否一致
   回答说: "GIL限制了所有并行" ← 过于绝对
   标准答案: "GIL限制了CPU密集型并行" ← 更准确
   → 不完全一致，扣分

③ 按事实一致程度给出 0~1 分数，并返回具体理由
```

**实际意义**：与忠实度的区别是——忠实度看「有没有瞎编」，事实正确性看「跟标准答案比对不对」。

**需要人工标注 reference**。

---

#### 答案完整性 (Answer Completeness)

**一句话**：回答有没有漏要点——即使回答事实没错，也要判断它是否覆盖了参考答案中的关键内容。

**比较对象**：`response`（AI 回答） vs `reference`（你写的标准答案）

**计算过程**：
```
① 平台原生 Judge 读取用户问题、AI回答和参考答案
② 把参考答案拆成关键要点
③ 判断 AI回答覆盖了多少要点
④ 返回 0~1 分数和具体理由
```

**实际意义**：分数低说明回答“答得不够全”。例如用户问年假政策，AI 只回答年假天数，但遗漏了“需提前 3 个工作日申请并审批”。

**需要人工标注 reference**。

---

#### HitRate@K (Hit Rate at K)

**一句话**：Top-K 命中率，判断前 K 个检索结果里有没有命中任一标准文档。

**比较对象**：`retrieved_context_ids` vs `reference_context_ids`

**计算过程**：
```
retrieved_context_ids = ["doc-a", "doc-b", "doc-c"]
reference_context_ids = ["doc-b"]

Top-3 中包含 doc-b → HitRate@3 = 1
```

**实际意义**：这是信息检索和 RAG 检索单测里的通用指标，也是检索器工程侧最直观的成功率指标。它不依赖 LLM，但要求每个检索片段都有稳定文档 ID。

---

#### MRR (Mean Reciprocal Rank)

**一句话**：平均倒数排名，判断第一个正确文档排在第几位，越靠前越好。

**比较对象**：`retrieved_context_ids` vs `reference_context_ids`

**计算过程**：
```
retrieved_context_ids = ["doc-a", "doc-b", "doc-c"]
reference_context_ids = ["doc-c"]

第一个命中文档 doc-c 排第 3 位 → MRR = 1/3 = 0.333
```

**实际意义**：这是信息检索领域衡量排序质量的通用指标。如果正确资料排得太靠后，生成模型可能被前面的噪声上下文干扰。

---

#### 任务完成度 (Task Completion)

**一句话**：Agent 是否真的把任务办完了，而不是只给了一个看似合理的回复。

**比较对象**：完整 Agent 轨迹 `user_input` vs `reference`（期望任务结果）

**计算过程**：
```
① 平台原生 Judge 阅读用户请求、工具调用、工具返回和最终回复
② 判断任务闭环是否完成
   例：用户要求“查订单并告知物流”，Agent 必须查到结果并告知用户，而不是只说“我来查”
③ 按完成程度给出 0~1 分数，并返回具体理由
```

**实际意义**：低分说明 Agent 没有完成任务、只完成部分任务，或最终回复没有把工具结果转化成用户需要的结果。

---

#### 工具正确性 (Tool Correctness)

**一句话**：Agent 调对工具了吗——调用的工具名称和参数是否与期望一致。

**比较对象**：对话中 AI 实际的 `tool_calls` vs 你标注的 `reference_tool_calls`

**计算过程**：
```
期望调用: [query_order(id="001"), create_return(id="001", reason="质量问题")]
实际调用: [query_order(id="001"), create_return(id="001", reason="不想要了")]

① 后端从 AI 消息中提取实际 tool_calls
② 对每个 reference_tool_calls 找完全匹配项：工具名和参数都必须一致
③ 分数 = 完全匹配的期望调用数 / 期望调用总数
```

**实际意义**：分数低说明 Agent 的**决策逻辑有问题**——调错了工具或传错了参数。

**需要人工标注 reference_tool_calls**。

**注意**：此指标**不需要 LLM**，是直接字符串比对。

---

#### 参数正确性 (Argument Correctness)

**一句话**：工具选对之后，参数有没有传对。

**比较对象**：同名实际工具调用的 `args` vs `reference_tool_calls` 中期望参数

**计算过程**：
```
期望调用: query_order(order_id="ORD-001", user_id="U-1")
实际调用: query_order(order_id="ORD-002", user_id="U-1")

① 后端先按工具名称匹配实际调用和期望调用
② 对同名工具逐项比较参数 key 和 value
③ 每个期望调用得到一个参数匹配度
④ 总分 = 所有期望调用的参数匹配度平均值
```

**实际意义**：它比 Tool Correctness 更细。Tool Correctness 要求工具名和参数完全一致；Argument Correctness 能告诉你“工具选对了，但参数错了多少”。

**注意**：此指标**不需要 LLM**，由后端代码确定性计算。

---

#### 步骤效率 (Step Efficiency)

**一句话**：Agent 是否用了合理数量的工具步骤，是否多调、漏调或重复调用。

**比较对象**：实际 `tool_calls` 数量 vs `reference_tool_calls` 数量

**计算过程**：
```
期望工具步骤数 = 2
实际工具步骤数 = 4

如果实际步骤数等于期望步骤数 → 1.0
如果多调或漏调 → 按接近程度扣分
例：2 / 4 = 0.5
```

**实际意义**：低分说明 Agent 执行路径不经济，可能重复查工具、绕路调用、漏掉关键步骤，影响成本、时延和稳定性。

**注意**：此指标**不需要 LLM**，由后端代码确定性计算。

---

#### 目标准确度 (Goal Accuracy)

**一句话**：任务完成了吗——Agent 最终有没有达成用户的目标。

**比较对象**：对话的最终结果 vs `reference`（你写的期望目标）

**计算过程**：
```
① 平台原生 Judge 阅读整段 Agent 轨迹，推断：
   - 用户目标: "查询订单物流"
   - 最终结果: "告知了用户快递单号和派送状态"

② 平台原生 Judge 将最终结果与你写的 reference 对比
   reference = "成功查询到物流状态"
   → 一致 → 1

③ 返回 0~1 分数和具体理由
```

**实际意义**：低分说明 Agent **没有完成任务或只完成了部分目标**。

---

#### 话题遵守度 (Topic Adherence)

**一句话**：AI 有没有跑题——对话中讨论的内容是否在你定义的话题范围内。

**比较对象**：对话中的话题 vs `reference_topics`（你定义的允许话题列表）

**计算过程**：
```
你定义 reference_topics = ["退货", "售后服务"]

① 平台原生 Judge 从对话中识别话题和越界内容：
   → "退货流程"、"退款金额"、"推荐其他商品"

② 平台原生 Judge 判断每个话题是否属于允许范围：
   → "退货流程" ∈ "退货" → ✓ 属于
   → "退款金额" ∈ "售后服务" → ✓ 属于
   → "推荐其他商品" → ✗ 不属于任何允许话题

③ 按话题遵守程度给出 0~1 分数，并返回具体理由
```

**实际意义**：分数低说明 AI **跑题了**，讨论了不该讨论的内容。

**reference_topics 从业务规则来**，不是从对话采集的。写一次，所有测试用例共用。

---

#### 轮次相关性 (Turn Relevancy)

**一句话**：每一轮 AI 回复是否回应了当前用户输入，而不是答非所问。

**比较对象**：每轮 `ai` 回复 vs 其前后的 `human` 输入和对话上下文

**计算过程**：
```
① 平台原生 Judge 按轮次阅读完整对话
② 对每个 AI 回复判断：
   - 是否回应当前用户问题
   - 是否忽略追问
   - 是否把上一轮上下文错误带入
③ 综合所有轮次给出 0~1 分数和具体理由
```

**实际意义**：低分说明多轮对话里有“当前轮没接住”的问题，常见于用户追问、补充约束或切换子问题时。

---

#### 对话完成度 (Conversation Completeness)

**一句话**：整段对话是否满足用户需求，并完成你在 `reference` 中定义的期望结果。

**比较对象**：完整 conversation vs `reference`

**计算过程**：
```
① 平台原生 Judge 阅读完整对话
② 判断用户最终需求是否被解决
③ 检查是否遗漏关键步骤、没有收束问题、没有给出可执行结论
④ 返回 0~1 分数和具体理由
```

**实际意义**：它看的是整段对话的结果，不是单轮是否漂亮。比如客服解释了退货政策但没有推进退货申请，就可能相关性高、完成度低。

---

#### 上下文记忆 (Knowledge Retention)

**一句话**：AI 是否记住用户前面已经说过的信息。

**比较对象**：后续 AI 回复 vs 用户前面给出的事实、偏好、限制、订单号、时间等

**计算过程**：
```
① 平台原生 Judge 从对话中抽取用户已提供的信息
   例：订单号 ORD-123、想退蓝牙耳机、明天下午上门
② 检查后续 AI 回复是否正确使用这些信息
③ 遗忘、混淆、前后矛盾或要求用户重复提供已给信息会扣分
```

**实际意义**：低分说明对话状态管理或 prompt 上下文保留有问题。

---

#### 角色遵守度 (Role Adherence)

**一句话**：AI 是否遵守指定角色、职责边界和语气要求。

**比较对象**：完整 conversation vs `reference_role`

**计算过程**：
```
reference_role = "电商客服助手：介绍优惠和商品信息，引导用户自助下单，不直接代替用户完成支付。"

① 平台原生 Judge 阅读 reference_role 和完整对话
② 判断 AI 是否保持角色和语气
③ 越权承诺、角色漂移、语气不合适或执行角色不允许的动作会扣分
```

**实际意义**：适合客服、销售、投顾、医疗咨询等强角色边界场景。比如客服助手承诺“我已替你付款下单”，就属于越权。

---

#### 轮次忠实度 (Turn Faithfulness)

**一句话**：多轮回复是否基于检索上下文或给定资料，没有跨轮幻觉。

**比较对象**：多轮 AI 回复 vs `retrieved_contexts`

**计算过程**：
```
① 平台原生 Judge 阅读 retrieved_contexts 和完整对话
② 判断每轮事实性回复是否能从资料得到支持
③ 与资料冲突、无依据承诺、跨轮捏造事实都会扣分
```

**实际意义**：这是多轮 RAG 或客服知识库场景的重要扩展指标。它能发现“第一轮答得对，后面越聊越编”的问题。

---

#### 连贯性 (Coherence)

**一句话**：回答逻辑通顺吗——AI 的回答是否条理清晰、没有前后矛盾。

**评判方式**：平台原生 Judge 阅读 response 或完整 conversation，判断是否逻辑通顺、条理清晰、前后不矛盾，给出 0（不连贯）或 1（连贯）并返回理由。

**不需要任何人工标注**。

---

#### 有害性 (Harmfulness)

**一句话**：回答有害吗——AI 的回答是否包含有害、欺骗性或危险内容。

**评判方式**：评测 LLM 独立阅读 response，给出 0（无害）或 1（有害）。

**不需要任何人工标注**。

---

## 六、实操建议

### 4.1 指标选择路线图

根据你的实际情况，选择合适的指标组合：

#### 第一阶段：零标注快速评测

**不需要写任何标准答案**，直接从系统日志采集数据就能跑。

| 场景 | 推荐指标 | 需要的数据 |
|------|---------|-----------|
| RAG | 忠实度 + 回答相关性 + 连贯性 | user_input, response, retrieved_contexts |
| Agent | 工具正确性/步骤效率（如已有期望工具）或任务完成度 | user_input（Agent 轨迹），可选 reference_tool_calls、reference |
| 多轮对话 | 轮次相关性 + 上下文记忆 + 话题遵守度 | user_input（human/ai 多轮对话），可选 reference_topics |

**能回答的核心问题**：AI 有没有瞎编？回答跑题了吗？回答通顺吗？有没有有害内容？

#### 第二阶段：关键用例精标注

为 10~20 个关键场景写标准答案（reference），增加更精确的评测。

| 场景 | 新增指标 | 额外需要的数据 |
|------|---------|---------------|
| RAG | + 事实正确性 + 上下文召回率 + 答案完整性 | reference（人工写的标准答案）|
| Agent | + Task Completion + Tool Correctness + Argument Correctness + Step Efficiency + Goal Accuracy | reference + reference_tool_calls |
| 多轮对话 | + Conversation Completeness + Role Adherence + Turn Faithfulness | reference + reference_role + retrieved_contexts |

#### 第三阶段：自定义业务指标

用 AspectCritic 创建针对业务的专属指标：

```
示例自定义指标：

「礼貌性」
  definition: "回复是否使用礼貌用语、态度友好？"
  → 0 = 不礼貌, 1 = 礼貌

「信息完整性」
  definition: "回复是否完整回答了用户所有的问题，没有遗漏？"
  → 0 = 有遗漏, 1 = 完整

「合规性」
  definition: "回复是否符合公司对外沟通的合规要求，没有透露内部信息？"
  → 0 = 不合规, 1 = 合规
```

### 4.2 数据采集方法

#### RAG 系统

```python
# 在你的 RAG 系统代码里，记录每次查询的输入输出
def query_with_logging(question):
    # 检索
    contexts = retriever.search(question)  # ← 这就是 retrieved_contexts

    # 生成
    answer = llm.generate(question, contexts)  # ← 这就是 response

    # 记录日志
    log = {
        "user_input": question,
        "response": answer,
        "retrieved_contexts": contexts,
    }
    save_to_file(log)  # 保存为 JSON，之后导入评测平台

    return answer
```

#### Agent 系统

```python
# 大多数 Agent 框架（LangChain/LangGraph/Swarm）都有消息记录
# 你需要把对话消息转成 human/ai/tool 格式

def collect_agent_trace(conversation_messages):
    trace = []
    for msg in conversation_messages:
        if msg.role == "user":
            trace.append({"type": "human", "content": msg.content})
        elif msg.role == "assistant":
            tool_calls = None
            if msg.tool_calls:
                tool_calls = [{"name": tc.name, "args": tc.arguments} for tc in msg.tool_calls]
            trace.append({"type": "ai", "content": msg.content, "tool_calls": tool_calls})
        elif msg.role == "tool":
            trace.append({"type": "tool", "content": msg.content})

    return {"user_input": trace}
```

#### 多轮对话系统

与 Agent 类似，收集 human/ai 交替的消息列表即可。如果不涉及工具调用，只需要 human 和 ai 两种类型。

### 4.3 标准答案（reference）怎么写

| 方法 | 适用场景 | 工作量 | 质量 |
|------|---------|--------|------|
| **人工编写** | 关键业务场景（10~20条） | 高 | 最高 |
| **从历史正确案例提取** | 已有质检通过的对话记录 | 中 | 高 |
| **用更强的 LLM 生成** | 大批量数据 | 低 | 中（需人工抽检） |
| **不写（用无标注指标）** | 日常监控 | 无 | 覆盖面有限 |

**推荐做法**：
1. 日常监控用无标注指标（忠实度 + 相关性 + 连贯性），自动化运行
2. 版本发布前用精标注用例（10~20 条关键场景 + 全部指标），确保不退化
3. 新场景上线时用 LLM 批量生成 reference，人工抽检 20% 后再用

### 4.4 评测结果怎么看

**看总览**：
- 通过率 > 80%：质量良好
- 通过率 60~80%：有改进空间，重点看低分指标
- 通过率 < 60%：需要重点优化

**看低分指标**：
| 低分指标 | 说明 | 改进方向 |
|---------|------|---------|
| 忠实度低 | AI 在编造检索文档里没有的内容 | 优化 prompt，增加「只基于提供的内容回答」的约束 |
| 上下文召回率低 | 检索漏了关键信息 | 优化检索策略、增加知识库覆盖度 |
| 上下文精确度低 | 检索了太多无关内容 | 提高检索阈值、优化分块策略 |
| 回答相关性低 | AI 跑题了 | 优化 prompt、增加 query 改写 |
| 事实正确性低 | 回答的事实与标准答案不一致 | 检查知识库是否过时、优化生成策略 |
| 上下文相关性低 | 检索内容整体和问题不贴合 | 优化召回查询、提高检索阈值、过滤噪声文档 |
| 任务完成度低 | Agent 没把任务闭环完成 | 优化任务规划、工具返回处理和最终回复模板 |
| 工具正确性低 | Agent 调错工具或工具+参数未完全匹配 | 优化工具描述、增加 few-shot 示例、调整工具选择策略 |
| 参数正确性低 | 工具选对但参数传错 | 检查参数抽取、实体识别、上下文槽位填充 |
| 步骤效率低 | Agent 多调、漏调或重复调用工具 | 优化 planner、减少无效重试、增加工具调用停止条件 |
| 目标准确度低 | Agent 最终结果与期望目标不一致 | 优化工具结果解释、任务完成判定和失败兜底 |
| 话题遵守度低 | AI 讨论了不该讨论的内容 | 增加 system prompt 的话题限制 |
| 轮次相关性低 | 多轮中某些回复没有接住当前用户问题 | 优化对话状态摘要和追问处理 |
| 对话完成度低 | 对话没有解决用户需求 | 优化收束策略、补齐关键业务流程步骤 |
| 上下文记忆低 | AI 忘记或混淆了用户前文信息 | 改进 memory、摘要、上下文窗口和字段抽取 |
| 角色遵守度低 | AI 越权、角色漂移或语气不符合要求 | 强化角色 system prompt 和拒答/转人工边界 |
| 轮次忠实度低 | 多轮回复脱离资料或跨轮幻觉 | 每轮注入必要上下文，约束只能基于资料回答 |

**看逐条明细**：
- 重点看失败行的**评分理由**（reason），这是评测 LLM 给出的具体解释
- 比如 reason 说「回答提到XX但上下文中没有相关信息」→ 说明这个知识点需要加入知识库

## 七、常见问题

### Q1: 评测 LLM 的打分准吗？

评测 LLM（如通义千问）的打分与人类评判的一致率通常在 **75%~85%** 之间。不是 100% 准确，但作为自动化监控工具已经足够。建议：
- 对分数接近阈值的边界案例，人工复查
- 定期抽样对比评测 LLM 与人工打分的一致性

### Q2: 用什么 LLM 做评测比较好？

推荐用**比被测系统更强的模型**做裁判：
- 被测系统用 GPT-3.5 → 用 GPT-4 做评测
- 被测系统用千问 → 用千问-Plus 或 GPT-4 做评测

不要用同一个模型既做被测系统又做裁判。

### Q3: 需要多少测试数据？

| 用途 | 建议数据量 |
|------|-----------|
| 快速验证/POC | 5~10 条 |
| 版本回归测试 | 20~50 条 |
| 正式评测报告 | 50~200 条 |
| 统计显著性分析 | 200+ 条 |

### Q4: 评测频率怎么定？

- **每次发版前**：跑完整回归测试（精标注用例）
- **每周/每天**：跑无标注监控（忠实度 + 相关性 + 连贯性），检测质量波动
- **线上异常时**：采集出问题的真实数据，补充到测试集，跑一次诊断
