# 评测系统的元评价指南（Meta-Evaluation）

> 评测系统的输出要支撑上线决策，那么**评测系统本身必须先被评测**。
> 本文档回答三个问题：指标测得准吗（效度）、测得稳吗（信度）、能分开好坏吗（区分度），
> 并给出与平台功能一一对应的可执行实验设计。
> 配套工具：`backend/scripts/compare_with_ragas.py`（与 RAGAS 对照实验）。

## 0. 为什么需要元评价

LLM 应用评测的三个现实问题：

1. **LLM-as-Judge 不是真值**——同一行样本，Judge 可能给出不同分数，甚至与人工判断相左；
2. **自研指标没有背书**——不套 RAGAS/DeepEval 意味着"分数含义"需要自己证明；
3. **分数会被"用错"**——如果指标分不出好坏，任何基于它的优化决策都是盲的。

元评价把评测系统当作被测对象，回答"这套分数我该信几分"。

## 1. 四个评测层次

### 1.1 效度（Validity）：测的是不是"那个东西"

| 方法 | 说明 | 平台对应 |
|------|------|----------|
| **准则效度**（最硬） | 以人工专家标注为黄金标准，计算自动分与人工分的一致性：Pearson / Spearman 相关、一致率、Cohen's Kappa | 报告"人工一致性"统计（`manual_auto_agreement_rate`）；人工复核流程 |
| **结构效度** | 与业界成熟框架（RAGAS）在同一批样本上的分数相关性——不替代人工，但证明"与主流判断方向一致" | `scripts/compare_with_ragas.py` |
| **已知组区分** | 构造已知好坏样本，验证分数能区分（见 1.3 与错误注入实验） | 数据集 + 评测执行 |

> 三种证据强度：人工一致性 > 已知组区分 > 与 RAGAS 相关。面试/汇报时按此优先级组织证据。

### 1.2 信度（Reliability）：测得稳不稳

| 方法 | 说明 | 平台对应 |
|------|------|----------|
| **重测信度** | 同一行样本重复评分 N 次，标准差越小越稳定；标准差超阈值标记低置信度 | `EVAL_JUDGE_SAMPLES=N` 多采样 + 报告 `judge_std_mean` / `low_confidence_count` |
| **评分者间一致性** | 两个不同 Judge 模型评同一批样本，Cohen's Kappa / 一致性率 | 配置多个 LLM 配置，同一场景换 Judge 跑两遍，报告对比 |
| **偏置检查** | 位置偏置（换序互评）、冗长偏置（length-controlled win-rate）、自我偏好偏置（同族模型互评）、格式偏置 | 盲测的左右随机化（md5）；对照实验可人工构造换序样本 |

### 1.3 区分度（Discrimination）：能不能分开好坏

- **错误注入实验**（推荐先做，成本最低）：取正确样本，注入典型错误（幻觉、事实错误、答非所问），
  看对应指标分数是否显著下降。示例结果（真实运行数据见下文实验记录）：
  - 正确基线：faithfulness ≈ 1.0
  - 注入"元组可变"幻觉：faithfulness 显著下降
  - 注入无关回答：answer_relevancy / faithfulness 双低
- **AUC 分析**（进阶）：以人工标注的好坏为二分类真值，指标分数作为判分器，计算 AUC——衡量指标"排序能力"。

### 1.4 实用性（Pragmatics）：用得起吗

- **成本**：Judge token 用量与估算成本（报告 `cost` 字段）；确定性指标零成本兜底的意义在此体现。
- **延迟**：逐行耗时（报告 execution_time_ms）。
- **稳定性**：Judge 调用失败率（error_count）。
- **可解释性**：每条分数是否带可读理由（平台逐条保存 Judge 理由，人工可复核）。

## 2. 实验 SOP

### 实验 A：与 RAGAS 的结构效度对照（最低成本、最高性价比）

```bash
cd backend
conda activate eval
pip install ragas==0.3.7 langchain-openai   # 一次性
python -m scripts.compare_with_ragas --dataset "RAG 示例数据集" --limit 20
```

要求：
- 样本量建议 **n ≥ 20**（n < 10 时相关系数无统计意义，仅作流程验证）；
- 数据集字段必须包含 `user_input` / `response` / `retrieved_contexts` / `reference`；
- `answer_relevancy` 需要 OpenAI 兼容 `/embeddings` 接口（默认 `text-embedding-v3`，可 `RAGAS_EMBEDDING_MODEL` 覆盖）；
- 结论口径：**Pearson/Spearman > 0.8 = 排序判断高度一致；0.6~0.8 = 方向一致，可结合人工抽检校准绝对分**。

> 说明：RAGAS 工具链指标（tool_call_accuracy 等）为多轮消息格式，与平台的数据集格式
> 不同。Agent 场景的对照建议改用"人工黄金集一致性"（实验 B），或自行做格式转换。

### 实验 B：人工黄金集一致性（准则效度，Agent 场景推荐）

1. 选取 20~50 条 Agent 样本（含正确/错误工具调用、正确/幻觉回复）；
2. 平台跑一遍评测 → 报告页逐条标记人工复核（pass/fail）；
3. 查看报告"人工一致性"统计：一致率 ≥ 85% 视为通过；分歧样本逐个分析（badcase 归因）；
4. 有分歧 → 定位是"指标口径问题"还是"标注问题"，修改判分标准（prompt_override）后重跑。

### 实验 C：错误注入区分度

1. 用 RAG 数据集生成器或手工构造 N 组样本：每组 = 正确样本 + 幻觉注入版 + 无关回答版；
2. 同一场景跑评测，对比三组分数；
3. 验收标准：faithfulness（幻觉注入组）与 answer_relevancy（无关回答组）应显著低于基线组。

### 实验 D：重测信度（Judge 稳定性）

```bash
EVAL_JUDGE_SAMPLES=5 python run.py   # 开启 5 次采样
```

1. 对同一数据集跑两遍评测（或同一遍开启多采样）；
2. 报告 `judge_std_mean` < 0.05 视为稳定；`low_confidence_count` 高的指标优先人工复核；
3. 换一个 Judge 模型（如 qwen-max）跑同一任务，报告对比看分数分布是否一致。

## 3. 结果如何汇报（面试/评审口径）

- **不要只说"我们做了评测"**，要说"我们评测了评测"：
  > 自研 Judge 指标与 RAGAS 在同一批样本上的 Spearman 相关性 0.85（n=30）；
  > 错误注入实验中，幻觉样本的 faithfulness 从 1.0 降至 0.3，区分度显著；
  > 5 次采样标准差均值 0.02，评分稳定；与人工复核一致率 92%。
- 数字要真实、注明样本量；n 小就明说"流程验证级"，并给出扩大样本的计划。

## 5. 实测记录（2026-08，真实运行数据）

以下数字由 `scripts/compare_with_ragas.py` 与平台评测引擎在 Qwen3.7-plus
（OpenAI 兼容 MaaS 网关）上真实运行产生，`ragas_comparison_report.json`
为脚本输出原始报告。

### 5.1 区分度实验（错误注入，3 行样本）

| 指标 | 正确基线 | 幻觉注入（"元组可变"） | 无关回答 |
|------|---------|----------------------|---------|
| faithfulness | 1.0 | 0.0 | 0.0 |
| factual_correctness | 1.0 | 0.0 | 0.0 |
| answer_relevancy | 1.0 | 0.1 | 0.0 |
| context_recall / precision | 1.0 | 1.0（不受生成侧污染影响） | 1.0 / 1.0 |

结论：生成侧指标对幻觉/答非所问敏感，检索侧指标保持稳定——验证了
"检索质量与生成质量解耦"的分层设计。

### 5.2 结构效度对照（RAGAS 0.3.7，n=25 混合集：9 正确 / 8 幻觉注入 / 8 截断）

> 本表为**缺陷 A（标签泄露）与缺陷 B（口径越界）双双修复后**的结果（见 5.3）。
> 此前两组数字均已作废：一组（faithfulness 0.584/0.686 等）在裁判可见样本真值
> 标签的条件下产生；另一组（context_recall 0.912、answer_relevancy 0.736 等）
> 在裁判可见口径外字段的条件下产生。
> 汇总报告：`ragas_comparison_report.json`（每个指标带 `_provenance` 标注来源）。
>
> 两个来源，按指标区分：4 个基础指标取自两个缺陷都修复后的重跑
> （`ragas_comparison_report_n25_scoped.json`）；2 个双通道指标标注"沿用"，
> 取自最早那次运行（`ragas_comparison_report_n25.json`）。沿用的依据是机制上的，
> 不是为了省调用量：`ClaimFaithfulnessMetric` 只读 `response` /
> `retrieved_contexts`，`GenerativeAnswerRelevancyMetric` 只读 `user_input` /
> `response`，两者都不经过 `_sample_payload`，因此**两个缺陷都碰不到它们**——
> 缺陷 A 的载体是兜底循环，缺陷 B 的载体是 sample 下发口径，这两条路径它们都不走。
> 代码层面亦可核验：两次修复的 diff 完全落在 `NativeBuiltinLLMMetric` 与
> `_sample_payload` 内，未触及这两个类。

| 指标 | 平台均值 | RAGAS 均值 | Pearson | Spearman | 数据来源 |
|------|---------|-----------|---------|----------|---------|
| faithfulness（整体判定） | 0.728 | 0.689 | 0.735 | 0.757 | 双修复后重跑 |
| **faithfulness_claim（断言级）** | 0.649 | 0.702 | **0.805** | **0.817** | 沿用（两缺陷均不涉及） |
| answer_relevancy（整体判定） | 0.744 | 0.809 | 0.373 | 0.239 | 双修复后重跑 |
| answer_relevancy_generative（生成式） | 0.913 | 0.816 | 0.571 | 0.545 | 沿用（两缺陷均不涉及） |
| context_precision | **1.000** | 1.000 | 双方无方差 | 无定义 | 双修复后重跑 |
| context_recall | **1.000** | 1.000 | 双方无方差 | 无定义 | 双修复后重跑 |

解读与边界：

1. **断言级忠实度是最强正面证据**：Pearson 0.805 / Spearman 0.817，落在
   ">0.8 = 排序判断高度一致"区间。这是同机制对标——RAGAS faithfulness 同为
   claim 级拆解 + 逐条判定，平台断言级指标与之机制对齐后一致性最高。
2. **双通道设计的独立价值在分层数据里显形**。与 RAGAS 的分层偏离（越小越贴合）：

   | | correct | hallucinated | truncated |
   |---|---|---|---|
   | 整体判定 | 0.000 | 0.102 | 0.225 |
   | 断言级 | 0.000 | 0.104 | **0.063** |

   截断样本上断言级的偏离只有整体判定的 **1/3.6**。机制解释：忠实度问的是
   "说出来的话有没有上下文支持"，不是"该说的话有没有说全"。截断样本不捏造内容，
   整体判定据此判它"忠实"（0.788）在定义上站得住；但 RAGAS 逐条拆解后，被截断的
   半句话构不成可验证的完整断言，因此给低分（0.563）。平台的断言级指标机制与
   RAGAS 对齐，也给出同向的低分——**这就是双通道不是"换个算法算出相似结果"的证据：
   同一批数据上两个通道给出了实质不同、且各自可解释的判断。**
3. **断言级优势在修复口径越界后反而变大**：Pearson +0.071 / Spearman +0.061
   （修复前 +0.047 / +0.007，泄露口径下曾虚高到 +0.168 / +0.123）。

   需要说清优势变大的机制，否则容易读成"修复让指标变好了"：整体判定失去
   `reference` 后，无法再看出"回答比参考答案少说了东西"，于是把截断样本判得
   更忠实（0.700 → 0.788），与 RAGAS 的距离拉大。**整体判定的定义纯度上升，
   与 RAGAS 的一致性下降**——两件事同时发生。断言级因机制本就与 RAGAS 对齐，
   不受影响，相对优势因此扩大。这不是断言级变强了，是整体判定回到了它该有的口径。
4. **answer_relevancy：口径越界已修复，修复后暴露出底下真实的机制差异**。
   修复前平台该指标声明只判"是否回应问题"，但裁判实际收到了 `reference`，
   于是把事实错误也算进扣分：幻觉样本平台 0.538 vs RAGAS 0.822。挡住
   `reference` 后，幻觉样本升到 0.850，与 RAGAS 的偏离从 0.284 塌到 **0.028**——
   越界那部分完全消失。

   但同一次修复让截断样本的偏离从 0.056 涨到 0.268，整体相关性反而略降
   （Pearson 0.439 → 0.373）。**这个方向必须如实记录**：原先的"中等相关"里有一
   部分是靠越界字段凑出来的巧合一致。裁判只看 user_input + response 时，截断回答
   会被判成两极——有的截断仍明显在回答问题（1.0），有的截断在答到之前就断了（0.0）；
   而 RAGAS 用反推问题 + embedding 相似度，截断回答仍保留话题词，反推问题语义不远，
   **结构上就惩罚不了截断**（8 条截断 RAGAS 给 0.60~0.98）。

   结论取向：**宁可要"指标只测它声明要测的东西"，也不要靠越界字段换一个更好看的
   相关系数**。要与 RAGAS 同机制对标，用的是 `answer_relevancy_generative`
   （同为反推问题 + 相似度），这正是双通道的分工。
5. **检索侧：修复后逐行等于 RAGAS，原先的方差被证明是 100% 的缺陷伪影**。
   RAGAS 侧 context_precision / context_recall 在全部 25 行均为 1.0——合成数据集的
   retrieved_contexts 直接取自源文档 chunk（= 完美检索），加样本不会产生方差。
   修复口径越界后，平台侧同样在全部 25 行给出 1.0，**逐行与 RAGAS 完全一致**
   （分层偏离 0.275 → 0.000 和 0.213 → 0.000）。

   这条是缺陷 B 修复最干净的验证：修复前平台侧那点方差（0.0/0.5/0.8/1.0）看着像
   检索质量信号，实测证明它一分不剩地来自"裁判看到了错误回答"。检索侧的结构效度
   仍无法用这个数据集验证——已改由 BM25 端到端检索实验补齐：无关干扰几乎不掉
   （MRR 1.0→0.98）、同域难负例单调下降（MRR 1.0→0.94，H@1 0.88→0.84），
   确定性指标能区分检索质量差异（详见元评价报告第四章 4.2）。
   平台侧出现的方差（0.0/0.5/0.8/1.0）**不是检索缺陷信号**，而是缺陷 B 造成的
   生成质量串入。
6. **天花板效应教训**：纯好样本集（n=25）上双方满分、相关系数无定义——
   证明评测集必须包含负样本，否则任何指标都"看起来很准"。

### 5.3 元评价反身性发现：评测集元数据泄露给裁判

对照实验的价值不止于"给自研指标背书"，它同时是对**评测平台自身效度**的检验。
本轮对照暴露两个平台缺陷，均由"平台分与 RAGAS 分在分层数据上系统性背离"这一
信号定位：

**缺陷 A：样本真值标签进入 Judge Prompt（已修复）**

评测集每行带 `generation_meta = {"kind": "correct|hallucinated|truncated"}`，
是构造数据时留下的真值标记。`_sample_payload` 的兜底循环会把样本内所有
非下划线字段无差别下发给裁判，标签因此进入 prompt——**100 个 judge prompt 中
64 个带标签，等于把答案交给判卷人**。指标区分度被系统性抬高，一致性也虚高
（裁判锚定标签后，换序互评自然更"稳定"）。

- 修复：`_JUDGE_HIDDEN_FIELDS` 不下发名单，`generation_meta` 永不进入 payload
- 回归测试：单元（`_sample_payload` 不含标签）+ 端到端（内置指标下发的
  payload 序列化后不含标签串）
- 验证：重跑 100 个 prompt，标签出现 0 次；关闭修复后泄露立即重现（测试非空转）

**缺陷 B：指标口径越界——声明的 required_fields 不约束实际下发字段（已修复）**

`required_fields` 仅用于校验字段"是否存在"，不用于裁剪 payload。结果是每个内置
指标都收到全部 7 个字段：

| 指标 | 声明口径 | 口径外收到的关键字段 |
|------|---------|-------------------|
| context_recall | reference, retrieved_contexts | **response** |
| context_precision | retrieved_contexts, user_input | **reference, response** |
| answer_relevancy | user_input, response | **reference, retrieved_contexts** |
| faithfulness | response, retrieved_contexts | **reference** |

后果是**通道污染**：检索侧指标本应只衡量"检索到的上下文够不够好"，与回答质量
无关——RAGAS 的 context_recall 在 25 行全部给 1.0（正确行为，它只读 reference
和 retrieved_contexts）。而平台 context_recall 在幻觉样本上掉到 0.725。标签泄露
（缺陷 A）已修复，故该方差只剩一个可能来源：payload 中依然可见的 `response`。

因果已由 A/B 实验证实（`backend/scripts/ab_response_leak.py`）。做法：在同一批
8 条幻觉样本上，对每条各打两次分，唯一差别是 payload 里有没有 `response`
（`generation_meta` 在两组中都已被缺陷 A 的修复屏蔽，故 `response` 是唯一变量）：

| 指标 | 带 response | 去掉 response | RAGAS | 受影响行 |
|------|-----------|-------------|-------|---------|
| context_recall | 0.7875 | **1.0000** | 1.000 | 3/8 |
| context_precision | 0.8125 | **1.0000** | 1.000 | 2/8 |

去掉 `response` 后，两个检索侧指标在全部 8 行上都回到 1.0，与 RAGAS 完全一致。
这说明平台检索侧指标的方差不是检索质量信号，而是裁判看到错误回答后把生成质量
算进了检索分。逐行配对（而非跨轮次均值对比）是这里的关键：跨轮次的
0.725 / 0.7875 差异属裁判采样波动，只有同批配对打分才能把 `response` 的效应
从噪声里分离出来。

这类缺陷靠单元测试发现不了（每个指标单独看都"正常返回分数"），只有跨框架对照
才能暴露：**两个实现同一语义的指标在同一批数据上系统性分歧，必有一方口径不对。**
这是元评价体系存在的实证理由。

**修复过程中的第二个发现：原定修复方案本身是错的**

上一版文档写的修复方向是"内置指标按 `required_fields` 严格裁剪 payload"。真去做
之前先枚举了全部 17 个内置指标，结果这个方案会**打断 9 个指标**：

- **8 个 Agent / 多轮指标**判的就是 AI 的回复，却都没把 `response` 列入
  `required_fields`——因为这类评测跑的是真实接口，回复在运行时才由
  `extract_eval_fields` 注入。提前列为必需会让 dataset 模式整批判"字段缺失"。
  按 `required_fields` 裁剪等于让 `turn_relevancy`、`knowledge_retention`、
  `role_adherence` 这些指标**看不见它们要评的那个回复**。
- **`context_precision`** 的判定文字明确写了"与用户问题及参考答案是否相关"，
  但 `reference` 不在它的 `required_fields` 里。裁剪后它会失去参考答案。

根因由此更清楚了：`required_fields` 一个字段被当成两件事用——

| | 语义 | 约束对象 |
|---|---|---|
| 校验门槛 | 数据集里必须有这些字段，否则不打分 | 静态数据集字段 |
| 可见范围 | 裁判能看到什么 | Judge Prompt 的 sample |

这两个集合本来就不相等，强行合并必然出错：要么放开（缺陷 B 的原貌），要么把
需要运行时字段的指标弄瞎（原定修复方案）。

**实际修复：引入独立的 `judge_fields` 口径**

- `prompt_manager.py` 给全部 17 个内置指标显式声明 `judge_fields`，与
  `required_fields` 并列、各管一件事；未声明时回退到 `required_fields`，
  保证新增指标默认收紧而非放开。
- `_sample_payload` 新增 `allow_fields` 白名单模式：给定时只下发名单内字段，
  **兜底循环整段跳过**（缺陷 A 和 B 的共同载体就是那个兜底循环）。内置指标走
  白名单；自定义 prompt 指标仍走原黑名单口径——它的可见范围由用户自己写的模板
  决定，平台不替用户裁剪。
- 修复后各指标实际下发的字段集（真实 Judge Prompt 抓取）：
  `faithfulness` = response + retrieved_contexts；`answer_relevancy` =
  user_input + response；`context_recall` = reference + retrieved_contexts；
  `context_precision` = user_input + reference + retrieved_contexts。
  检索侧不再有 `response`，`answer_relevancy` 不再有 `reference`。

回归测试 5 个，其中一个专门防**过度修正**——断言 8 个 Agent/多轮指标仍能看到
`response`。撤掉修复后，3 个防缺陷测试立刻失败，而这个防过度修正的测试仍然通过
（修复前本来什么都看得见），说明两个方向都有测试把着。

这一段本身也是元评价的一部分：**"先枚举全部受影响对象，再动手"** 挡住了一个
会让 9 个指标静默失效的修复。缺陷 B 的教训不止"口径要收紧"，还有"收紧的依据
必须是每个指标真正需要什么，而不是它恰好声明了什么"。

**修复后实测（n=25 同一数据集，RAGAS 逐行分复用、逐行核对未变）**

| 指标 | 平台修复前 | 平台修复后 | RAGAS | 与 RAGAS 分层总偏离 前→后 |
|------|----------|----------|-------|----------------------|
| context_recall | 0.912 | **1.000** | 1.000 | 0.275 → **0.000** |
| context_precision | 0.932 | **1.000** | 1.000 | 0.213 → **0.000** |
| faithfulness | 0.692 | 0.728 | 0.689 | 0.264 → 0.327 |
| answer_relevancy | 0.736 | 0.744 | 0.809 | 0.440 → **0.330** |

检索侧是干净的胜利：两个指标修复后在全部 25 行上**逐行等于 RAGAS**（distinct 值
只有 `[1.0]`）。这反过来完成了一个此前只能推断的判断——平台检索侧那点方差
**百分之百是缺陷 B 的产物，没有一丝是检索信号**。相关系数现在是 `nan`，但这次是
正确的 `nan`：双方都是常量，不是平台有虚假方差。

生成侧要如实说明：**口径正确性上升，与 RAGAS 的相关性反而略降。**

| | Pearson 前→后 | Spearman 前→后 |
|---|---|---|
| faithfulness | 0.759 → 0.735 | 0.811 → 0.757 |
| answer_relevancy | 0.439 → 0.373 | 0.340 → 0.239 |

不修饰这个结果，但要解释清楚它的成因——**泄露此前掩盖了一个真实的机制差异**：

- `answer_relevancy` 在幻觉样本上的偏离从 0.284 崩到 0.028（缺陷 B 生成侧那一半
  确实治好了，指标不再惩罚事实错误）；但截断样本上偏离从 0.056 涨到 0.268。
  原因：拿掉 `reference` 后裁判只看问题和回答，于是对"截断"给出两极分化的判断
  （回答被截断在答到问题之前 → 0，截断在之后 → 1）。RAGAS 那侧做的是反推问题 +
  embedding 相似度，截断的回答仍有话题内容，反推问题依然贴近原问题，所以分数普遍
  偏高（0.60~0.98）——它**结构上就惩罚不了截断**。修复前平台能看到参考答案，
  得以给出"不完整"的中间分，恰好落在 RAGAS 的中间分附近：**对的分数，错的理由**。
- `faithfulness` 同理。忠实度问的是"说出来的话有没有上下文支撑"，不是"该说的有没有
  说全"。拿掉 `reference` 后，不捏造内容的截断样本按定义就是忠实的，平台分从 0.70
  升到 0.79；RAGAS 因为做 claim 级拆解，把截断的半句话算作无法验证的断言，给 0.56。

结论：这不是修复造成的退步，而是**修复把一个被泄露掩盖的机制差异暴露了出来**。
在"与另一个框架的相关性"和"指标符合自己声明的口径"之间，本项目选后者——
前者可以靠不修 bug 刷高，后者才是指标能被信任的前提。

顺带一个提醒：这些相关性变化幅度不大（0.02~0.10）且 n=25，裁判采样波动本身就能
解释一部分，不宜过度解读。真正大而明确的是结构性结论：检索侧偏离归零、幻觉样本
偏离从 0.284 崩到 0.028。
