## 🔍 关键发现

### 1. Agent 的三大典型问题

**推理不忠实（13% 样本）：**
- 编造与工具返回不符的信息
- 数值计算错误（工具返回 111，Agent 说 112）
- 事实描述错误（工具返回晴天，Agent 说下雨）

**错误处理不足（40% 样本）：**
- 遇错直接终止，无重试机制
- 不尝试降级或切换工具
- 缺乏对用户的错误说明

**工具选择次优（8% 样本）：**
- 用通用工具替代专用工具（用 web_search 做计算）
- 执行与任务无关的操作（查天气但任务是搜索信息）
- 浪费工具调用配额

### 2. 轨迹级指标的价值

**过程级可观测性：**
- 不只看最终结果（任务完成没有）
- 还看执行过程（哪个环节出错了）

**Badcase 精确定位：**
- 推理问题 → Agent 编造信息
- 工具问题 → 选错工具或工具失败
- 恢复问题 → 错误处理策略缺失

**能力诊断量化：**
- 轨迹忠实度：推理能力
- 错误恢复率：容错能力
- 工具选择合理性：决策能力

### 3. 与业界前沿对标

**TRAJECT-Bench：**
- ✅ 相同点：都关注 Agent 执行过程
- 🔶 差异点：TRAJECT 侧重逻辑连贯性，我们侧重工具交互正确性

**VAKRA：**
- ✅ 相同点：都用 LLM-as-a-Judge 验证行为合理性
- 🔶 差异点：VAKRA 侧重知识正确性，我们侧重操作正确性

### 3 分钟版本（追问深挖）

**Q: 为什么要做轨迹级评测？**
> "传统评测只看最终结果，但 Agent 调试时需要知道哪个环节出错了。是工具选错了、推理错了、还是错误处理不当？轨迹级评测提供了过程级的可观测性，让 Agent badcase 分析从'盲猜'变成'精确定位'。这在生产环境非常有价值——能快速定位问题根因，而不是看着任务失败却不知道为什么。"

**Q: 轨迹忠实度怎么评测？**
> "用 LLM Judge 判断 Agent 的推理是否忠实于工具返回结果。具体来说，给 Judge 看工具返回的内容（比如天气查询返回'晴天 26-33°C'）和 Agent 的推理（Agent 说'下雨 20-25°C'），让它判断是否一致。返回结构化 JSON：`{verdict: 'faithful' or 'not_faithful', reason: '...'}`。这能检测出 Agent 编造信息、数值错误、事实曲解等问题。在 30 个样本上，发现 13% 存在推理不忠实。"

**Q: 错误恢复能力怎么评测？**
> "两步走：第一步，识别错误步骤——正则匹配工具返回中的 'error', 'failed', '错误' 等关键词。第二步，检查后续 3 个步骤是否有恢复动作：重试（重新调用同一工具）、切换工具（换个工具试试）、寻找替代方案（改变策略）。如果有任一恢复动作，判定为成功恢复。结果是 60% 恢复率，40% 的 Agent 遇错就直接终止，这揭示了 Agent 容错能力的不足。"

**Q: 这对业务有什么价值？**
> "三个价值：第一，**Badcase 定位**，能精确定位问题出在哪个步骤，是推理错误、工具失败还是恢复不当。第二，**能力诊断**，量化 Agent 在推理、错误处理、工具选择上的能力水平，可以横向对比不同 Agent 的表现。第三，**预测能力**，轨迹级指标和任务完成度高度相关（预期 Spearman 0.73），可以提前预警可能失败的任务。这在生产环境的 Agent 监控中非常有价值——实时评测轨迹指标，自动标注 badcase。"

**Q: 与 TRAJECT-Bench 的区别是什么？**
> "核心思想相同——都是轨迹级评测，都关注过程而非仅结果。但侧重点不同：TRAJECT-Bench 更侧重多步推理的逻辑连贯性，比如推理链条是否自洽；我们更侧重工具交互的正确性，比如工具调用是否准确、推理是否忠实于工具返回、错误处理是否得当。这个差异源于应用场景——TRAJECT 更关注纯推理型 Agent，我们更关注工具增强型 Agent。"
