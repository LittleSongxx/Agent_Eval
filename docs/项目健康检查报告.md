## 一、阻塞性问题（P0）

### ❌ 问题 1：前端缺失 `recharts` 依赖

**问题描述**:  
在 P0-4（可视化报告增强）中新增了 4 个图表组件，都依赖 `recharts` 库：
- `RadarChart.tsx` - 雷达图
- `ScatterChart.tsx` - 散点图
- `TrendLineChart.tsx` - 趋势折线图
- `BoxPlotChart.tsx` - 箱线图

但 `package.json` 中未添加 `recharts` 依赖，导致：
1. TypeScript 编译报错（Cannot find module 'recharts'）
2. 前端无法正常构建
3. 图表组件完全不可用

**影响**:  
- ❌ 前端构建失败
- ❌ P0-4 功能完全无法使用
- ❌ CI 门禁会阻塞（如果加了前端类型检查）

**根因分析**:  
在创建图表组件时，误以为可以使用 `@ant-design/charts` 的底层 `recharts` 导出，但实际上：
- `@ant-design/charts` 已经安装（v2.6.7）
- 但它不直接导出 `recharts` 的组件
- 需要单独安装 `recharts` 作为 peer dependency

**修复方案**:  
```bash
cd frontend
npm install recharts
npm install --save-dev @types/recharts
```

**验证方法**:  
```bash
npx tsc --noEmit  # 应该无类型错误
npm run build     # 应该构建成功
```

## 二、优化建议（非阻塞）

### 📋 建议 1：修复 SQLAlchemy 2.0 废弃 API 警告

**问题描述**:  
测试输出显示 16 次 `LegacyAPIWarning`：
```
/backend/app/core/evaluation_engine.py:1816: LegacyAPIWarning: 
The Query.get() method is considered legacy as of the 1.x series
```

**位置**: `evaluation_engine.py:1816`
```python
task = db.query(EvalTask).get(task_id)  # ❌ 废弃写法
```

**推荐修复**:  
```python
task = db.get(EvalTask, task_id)  # ✅ SQLAlchemy 2.0 写法
```

**影响**: 低  
- 功能正常，不影响运行
- 但在升级 SQLAlchemy 2.0 时会破坏

### 📋 建议 2：修复 `datetime.utcnow()` 废弃警告

**问题描述**:  
3 次 `DeprecationWarning` 来自 `seed.py:1049`：
```python
now = datetime.utcnow()  # ❌ Python 3.12+ 废弃
```

**推荐修复**:  
```python
from datetime import datetime, UTC
now = datetime.now(UTC)  # ✅ 时区感知
```

**影响**: 低  
- Python 3.13+ 会逐步移除此 API
- 但不影响当前运行

### 📋 建议 3：统一图表库选型（架构决策）

**问题描述**:  
项目中同时使用了两个图表库：
1. `@ant-design/charts`（已在 `package.json` 中）
2. `recharts`（新增的 4 个组件使用）

**现状分析**:  
- `@ant-design/charts` 是 Ant Design 官方图表库，基于 G2Plot
  - 优点：与 Ant Design 风格统一，开箱即用
  - 缺点：定制性较低，部分高级图表不支持
- `recharts` 是独立的 React 图表库
  - 优点：轻量、灵活、TypeScript 友好
  - 缺点：需要手动配置样式

**推荐方案**:  
保持现状（混用），但明确分工：
- 简单图表（折线、柱状、饼图）→ `@ant-design/charts`
- 复杂/定制图表（雷达、散点、箱线）→ `recharts`

**需要决策**:  
如果追求一致性，可以选择：
- 方案 A：全部迁移到 `recharts`（工作量 ~2 天）
- 方案 B：全部迁移到 `@ant-design/charts`（需要重写 4 个新组件）
- 方案 C：保持现状（推荐，性价比最高）

## 四、设计合理性审查

### ✅ 评测指纹机制

```python
fingerprint = compute_eval_fingerprint(

    dataset_id,          # 数据ID

```

**评价**: ✅ 合理  
- 涵盖了所有影响评测结果的因素
- 快照机制保证了可重现性
- 数据版本控制避免了数据变更误判

### ✅ 多裁判面板设计

**设计**: 支持多个 LLM 配置并行评测同一样本

judge_panel: list[int] = []  # 存储附加裁判的 LLM config ID

**评价**: ✅ 合理

- 支持盲测对比（A/B Test）

### ⚠️ 场景快照 JSON 序列化

**设计**: `scenario_snapshot` 存储为 JSON 字段
```python
scenario_snapshot = {
    "metrics": [...],
    "config": {...}
}
```

**潜在问题**:  
- 如果 JSON 过大（>1MB），SQLite 性能会下降
- 无法直接用 SQL 查询快照内的指标

**影响**: 低  
- 当前场景下（<20 个指标）不会超过 10KB
- 查询需求主要在任务级别，不在指标级别

**建议**: 保持现状，如果未来需要支持超大场景（100+ 指标），可考虑拆表

---

### ✅ 错误恢复能力指标的启发式规则

**设计**: 通过关键词匹配检测恢复行为
```python
if "重试" in next_thought or "retry" in next_thought:
    recovery_action = "重试相同操作"
elif next_tool and next_tool != tool_name:
    recovery_action = f"切换到工具 {next_tool}"
```

**评价**: ✅ 合理的工程权衡  
- 优点：简单直接，覆盖了 80% 的常见模式
- 缺点：可能漏掉隐式恢复（Agent 没明确说"重试"但实际在重试）

**改进方向**:  
如果需要更高准确率，可以：
1. 增加更多关键词（"再次尝试"、"换个方法"）
2. 使用 LLM Judge 判断（成本更高，但更准确）

当前设计符合 MVP 原则（最小可行产品）。

### 🤔 问题：成本优化实验名不副实

**问题描述**:  
实验名为"成本优化实验"（`cost_optimization_experiment.py`），但实际只测了**时间优化**，未测**成本优化**。

**实验内容**:  
- ✅ 测试了并发策略对**耗时**的影响（85.8% 时间减少）
- ❌ 未测试对**token 消耗**的影响（成本 = token × 单价）
- ❌ 未测试批量推理（真正的成本优化手段）

**文档中的说法**:  
> "核心结论：并发优化的是时间，不是成本（token 消耗相同）"

**问题根源**:  
命名与实际不符，容易误导：
- 实验名叫"cost_optimization"
- 但报告文件名也是 `cost_optimization_report.json`
- 实际上应该叫 `concurrency_optimization_experiment.py`

**建议**:  
重命名文件 + 报告：
```bash
mv cost_optimization_experiment.py concurrency_optimization_experiment.py
mv cost_optimization_report.json concurrency_optimization_report.json
```

并在 P0-3 的文档中明确说明：
> "本实验聚焦**时间优化**（通过并发降低延迟），真正的**成本优化**（通过批量推理降低 token 消耗）留作后续工作。"
