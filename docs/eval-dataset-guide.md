# 评测数据集构建指南

> 本文档回答一个问题：**如何构建一套可信、可复用、抗污染的评测数据集**。
> 内容与平台功能一一对应，是评测实验设计的方法论说明，也可以作为面试中
> "评测集怎么建"这一追问的标准回答素材。

## 1. 为什么评测集本身值得认真设计

评测结果的可信度 = 评测集的质量 × Judge 的稳定性。

- 评测集质量差（样本同质、覆盖单一），再稳定的 Judge 也只能证明"这个模型在
  这 20 个类似问题上表现不错"，无法支撑上线决策。
- 评测集被污染（公开问题已进入模型预训练数据、或评测样本被用于调 Prompt），
  指标会虚高，"命中率 90%"并不代表真实业务能力。
- 因此评测集要有**分层覆盖**、**标注规范**和**防污染机制**，这三点是本平台的
  数据集管理（field_schema、行级数据、CSV/JSON 导入导出）所支撑的。

## 2. 样本来源：优先真实，辅以合成

按优先级推荐：

| 来源 | 说明 | 平台对应 |
|------|------|----------|
| 线上真实用户问题 | 日志采样（脱敏后），最贴近真实分布 | 数据集 CSV 导入 |
| 历史 Badcase | 上线后效果不佳的样本，防止回归 | 报告 → 人工复核标记 needs_fix 后回流 |
| 业务 FAQ / 文档变更点 | 覆盖知识库高频查询 | 数据集手动录入 |
| 大模型合成（文档 → QA） | 用于冷启动扩充，需人工抽检 | RAG 数据集生成器 |

> ⚠️ 合成样本必须人工抽检。本平台 RAG 生成器虽然内置了"生成 → 自校验 →
> 按质量截断"的流水线，但生成质量仍依赖文档质量，**上线前建议对生成的
> 样本做一轮人工确认**（数据集行级编辑即可完成）。

## 3. 分层覆盖：四类必测场景

单轮 RAG 评测集至少覆盖四类场景（Agent / 多轮评测可参考此思路拆层）：

| 场景 | 定义 | 设计意图 | 样例字段 |
|------|------|----------|----------|
| 找得到（正例） | 知识库存在明确答案，且检索可命中 | 验证主链路效果 | `user_input` + `reference` + `reference_context_ids` |
| 找不到（拒答） | 知识库没有答案，应拒答或引导 | 验证幻觉防线 | `user_input` + `reference`（期望拒答口径） |
| 过期/冲突知识 | 知识已更新，模型不应答旧版本 | 验证时效性 | `user_input` + `reference`（新版本答案） |
| 权限/越权 | 不在权限范围内的内容不应回复 | 验证安全边界 | `user_input` + 期望拒答理由 |

正负样本比例建议 **7:3 左右**（正例为主，但拒答类样本必须有足够量，否则
"回答不了"的场景从未被测过）。

## 4. 指标分层：检索侧、生成侧、任务侧分开看

同一个评测任务里建议同时配置不同层的指标，便于定位问题：

- **检索侧**（本平台确定性指标，零 LLM 成本）：`HitRate@K`、`MRR` —— 检索
  质量与生成质量解耦，检索变差时能第一时间定位。
- **生成侧**（LLM Judge）：`faithfulness`（忠实性）、`answer_relevancy`、
  `factual_correctness` —— 判断回答内容本身的质量。
- **任务侧**（Agent 场景）：`task_completion`、`tool_call_accuracy`、
  `argument_correctness`、`step_efficiency` —— 判断任务是否通过正确的工具
  调用完成。

> 检索侧全部用确定性指标，生成侧才调用 LLM Judge——这是刻意设计：既控制
> 成本，也让"检索变差"和"生成变差"成为两个独立可定位的信号。

## 5. 防污染：为什么指标会虚高，怎么防

**污染路径**：① 公开文档/问题进入模型预训练数据（模型"背过答案"）；
② 评测样本被反复用于 Prompt 调优（过拟合评测集）。

**平台内的实操建议**：

1. **优先使用私有或未见过的文档**构建评测集；公开文档（如常见开源项目
   README）已在预训练数据中的概率很高，命中率虚高。
2. **时间隔离**：知识库文档更新后，用新版本重建评测样本，避免旧版本答案
   被误判为错误。
3. **动态私有题**：在正式评测前，用 RAG 数据集生成器基于私有文档生成一批
   新问答，作为回归集的一部分。
4. **n-gram 重叠检查**：导出评测集后，抽样比对样本问题与训练语料的 n-gram
   重叠度，重叠过高的样本标记为"疑似污染"，单独观察或剔除。
5. **不让评测集"过拟合"**：评测报告（本平台报告对比功能）应作为迭代入口，
   每个 Prompt/检索调整都要跑同一套回归集，并记录通过率与加权总分的变化；
   不要只盯着通过率绝对值，要看**相对基线的变化**。

## 6. 样本量与置信度

- 冷启动：每场景 **50–200 条**（分层覆盖后），足够发现主要问题。
- 回归集：**200–500 条**，覆盖四类场景 + 历史 Badcase。
- 上线前 A/B：样本量越大越好，结合人工盲测（平台盲测功能）做最终判断。
- 上线决策建议用**加权总分 + 样本通过率 + 人工抽检一致率**三个数字一起看，
  单一指标容易骗人。

## 7. 迭代闭环（数据飞轮）

```text
线上日志/人工标记 Badcase
        ↓
评测集更新（新增/修正样本）
        ↓
回归评测（同一场景快照 + 报告对比）
        ↓
定位问题（检索侧 or 生成侧）
        ↓
优化（Chunk/召回/Prompt/模型）
        ↓
回归确认（通过率、加权总分变化）
        ↓
上线（结合人工盲测）
```

平台里每一步都有对应功能：数据集管理（第 1 步）、评测任务 + 场景快照
（第 2-3 步）、指标分层与报告（第 4-5 步）、报告对比（第 6 步）、盲测
（第 7 步）。

## 8. 数据字段约定

评测样本统一使用以下字段名，平台内置指标按这些字段取数：

| 字段 | 类型 | 用途 |
|------|------|------|
| `user_input` | string / conversation 数组 | 用户输入（多轮为对话数组） |
| `response` | string | 被测系统输出 |
| `reference` | string | 标准答案 |
| `retrieved_contexts` | string[] | 检索到的上下文 |
| `reference_contexts` | string[] | 标准检索上下文（评测集自带） |
| `retrieved_context_ids` | string[] | 检索到的文档 ID（用于 HitRate@K/MRR） |
| `reference_context_ids` | string[] | 标准命中文档 ID |
| `reference_tool_calls` | object[] | Agent 场景期望的工具调用序列 |
| `reference_topics` | string[] | 多轮对话期望话题（topic_adherence） |
| `reference_role` | string | 期望角色行为（role_adherence） |

字段缺失时指标会返回"缺少必需字段"并在报告中标记 error，评测集 schema
校验（字段级 required 标记）可以在导入时尽早暴露问题。
